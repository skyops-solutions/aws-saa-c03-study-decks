Розділ 1

Docker та Amazon ECS

Контейнери — легша альтернатива віртуальним машинам

Docker (як для 5-річного)

Контейнер для перевезення — той самий вантаж, будь-де

  • Уяви стандартизований морський контейнер: неважливо, який корабель чи вантажівка — контейнер підходить всюди однаково.
  • Docker 'запаковує' застосунок + всі його залежності в один переносний 'образ' (image), що працює ІДЕНТИЧНО на будь-якому сервері з Docker.
  • На відміну від EC2 (повна віртуальна машина зі своєю ОС), контейнери ДІЛЯТЬ ядро ОС хоста — легші, швидше стартують.
EXAM TIPКонтейнер — не віртуальна машина. Кілька контейнерів на одному хості діляться одним ядром ОС, тому вони значно 'легші' за окремі EC2-інстанси.
1. Docker & Amazon ECS

Amazon ECS

Elastic Container Service — оркестрація Docker-контейнерів

  • Task DefinitionJSON-опис 'рецепту': який образ, скільки CPU/RAM, які порти — аналог Launch Template для контейнерів.
  • Taskодин запущений екземпляр Task Definition (аналог EC2-інстансу для контейнера).
  • Serviceпідтримує задану кількість Tasks запущеними одночасно (аналог Auto Scaling Group для контейнерів), інтегрується з ALB.
  • Clusterлогічне групування, де виконуються Tasks.
EXAM TIPTask Definition → Service → Cluster — та сама ієрархія логіки, що Launch Template → ASG → (набір AZ) в світі EC2.

2. Launch Types: EC2 vs Fargate

Amazon ECR

Elastic Container Registry — де зберігаються Docker-образи

  • Приватний (або публічний) репозиторій для Docker-образів — аналог 'S3 для контейнерних образів'.
  • Інтегрований з IAM для контролю доступу, підтримує сканування образів на вразливості (Image Scanning), lifecycle policies для автоматичного видалення старих образів.
  • ECS/EKS Task витягує (pull) образ саме з ECR перед запуском контейнера.

Розділ 3

Amazon EKS та архітектурні патерни

Керований Kubernetes і типові сценарії

Amazon EKS

Elastic Kubernetes Service — керований Kubernetes

  • Kubernetes — open-source оркестратор контейнерів (не AWS-специфічний), популярний за межами AWS теж — багато компаній хочуть 'мультихмарну' сумісність.
  • EKS керує Kubernetes control plane (API server, etcd тощо) за тебе — так само як ECS, але за стандартом Kubernetes, а не власним AWS-форматом.
  • Worker nodes можуть бути EC2 (ти керуєш) або EKS Fargate (serverless, AWS керує) — та сама дилема launch type, що й у ECS.
EXAM TIP'Компанія вже використовує Kubernetes на іншій хмарі/on-premises і хоче перенести без переписування маніфестів' → EKS (не ECS, який використовує власний формат AWS).

3. Amazon EKS & Solution Architectures

IAM для окремих Pod в EKS (IRSA)

Чому 'права на рівні EC2-хоста' — недостатньо гранулярно

  • Проблема: у Kubernetes-кластері на одному EC2 worker node одночасно можуть працювати Pod'и РІЗНИХ застосунків. Якщо дати IAM-права через звичайний EC2 Instance Profile — ВСІ Pod'и на цьому хості отримають ОДНАКОВІ права, навіть якщо їм потрібен доступ до різних ресурсів.
  • IRSA (IAM Roles for Service Accounts) вирішує це: дозволяє прикріпити ОКРЕМУ IAM Role до КОНКРЕТНОГО Kubernetes Service Account — тобто окремий Pod отримує лише ТІ права, які потрібні саме йому, незалежно від інших Pod'ів на тому самому хості.
ЗАПАМ'ЯТАЙ'Потрібно дати різні IAM-права різним Pod'ам на одному EKS-вузлі' → IRSA. Права на рівні EC2 Instance Profile тут занадто грубі — вони поширюються на ВСІ Pod'и хоста одразу.
3. Amazon EKS & Solution Architectures

Типові архітектурні патерни з контейнерами

Практичні сценарії іспиту

  • ECS + ALBрозподіл трафіку між Tasks у Service — так само, як ALB розподіляє трафік між EC2 в ASG.
  • ECS Auto ScalingService Auto Scaling (кількість Tasks) окремо від Cluster Auto Scaling (кількість EC2-хостів, якщо launch type = EC2).
  • Batch processing з Fargateзапуск короткочасних контейнерних задач без потреби тримати EC2-парк 'напоготові' постійно.
  • CI/CD з ECR + ECSтиповий deployment pipeline: build image → push в ECR → ECS Service підтягує нову версію (rolling update).
ЗАПАМ'ЯТАЙ'Потрібно періодично запускати batch-задачі без витрат на постійно працюючі EC2' → ECS/EKS на Fargate — плата лише за фактичний час виконання задачі.

Підсумок: Containers одним поглядом

  • Docker: легші за VM, діляться ядром ОС хоста, переносні 'образи' застосунків
  • ECS: AWS-специфічний оркестратор (Task Definition → Task → Service → Cluster)
  • EC2 launch type (керуєш хостами сам) vs Fargate (serverless, платиш за факт. CPU/RAM)
  • ECR: приватний registry для образів. EKS: керований Kubernetes — для портативності/мультихмарності

Головне питання цього розділу завжди зводиться до: 'хто керує серверами?' (EC2 vs Fargate) і 'який формат оркестрації?' (ECS vs EKS).
