Розділ 1

EBS та AMI

Диск для одного інстансу і 'знімок' для повторного використання

Amazon EBS

Elastic Block Store — віртуальний жорсткий диск

  • EBS — це мережевий блоковий диск, який 'підключається' (attach) до ОДНОГО EC2-інстансу за раз (крім Multi-Attach), схожий на звичайний SSD/HDD.
  • Прив'язаний до КОНКРЕТНОЇ Availability Zone — щоб перенести том в іншу AZ, спочатку роблять snapshot, потім відновлюють том з нього в потрібній AZ.
  • Живе НЕЗАЛЕЖНО від інстансу: можна від'єднати диск від одного EC2 і приєднати до іншого (дані збережуться).
  • EBS Multi-Attach: дозволяє прикріпити ОДИН io1/io2 том до КІЛЬКОХ інстансів ОДНОЧАСНО в тій самій AZ (лише для спеціалізованих кластерних застосунків з власним контролем конкурентного запису).
EXAM TIPEBS том 'живе' в одній конкретній AZ. Це ключова відмінність від EFS (multi-AZ) — часте питання на іспиті.

Обираємо за IOPS/throughput/ціною

ТипКатегоріяТиповий сценарій

1. EBS & AMI

AMI, Snapshots, Encryption

Резервні копії та шаблони

  • EBS Snapshotpoint-in-time резервна копія тому, зберігається в S3 (керується AWS, ти S3 bucket не бачиш); інкрементні (тільки зміни з часу останнього snapshot).
  • AMI (Amazon Machine Image)шаблон для запуску нових інстансів: ОС + встановлений софт + прикріплені EBS snapshots. Можна створити AMI з ІСНУЮЧОГО інстансу для 'клонування' налаштувань.
  • Копіювання snapshot між регіонамистандартний спосіб перенести AMI/дані в інший регіон для DR.
  • EBS Encryptionшифрування через KMS; знімки з зашифрованого тому — теж зашифровані; можна зашифрувати НЕзашифрований том лише через snapshot → copy with encryption → створити новий том.
EXAM TIP'Перенести AMI в інший регіон для DR' → Copy AMI (яка автоматично копіює прикріплені snapshots) в цільовий регіон.
1. EBS & AMI

Пастки практичних тестів: EBS

Обмеження, які завжди перевіряють

  • EBS Multi-Attach — ТІЛЬКИ io1/io2не gp2/gp3, не st1/sc1. Якщо в питанні 'Multi-Attach' згадано разом з gp3 — це автоматично неправильна відповідь.
  • st1 і sc1 НІКОЛИ не можуть бути boot volumeце HDD-типи, оптимізовані для послідовного читання великих обсягів (data warehousing, logs) — вони фізично не призначені для завантаження ОС. Лише gp2/gp3/io1/io2 можуть бути root volume.
EXAM TIPПрактичні тести люблять комбінувати ці обмеження в одному питанні: 'обери найдешевший тип для boot volume з Multi-Attach' — пастка, бо жоден дешевий HDD-тип не може бути ні boot volume, ні Multi-Attach.

Розділ 2

EFS, FSx та Instance Store

Спільні файлові системи та тимчасове сховище

Amazon EFS

Elastic File System — NFS, доступний з БАГАТЬОХ інстансів одночасно

  • На відміну від EBS (один інстанс), EFS можна ПОДІЛЯТИ між сотнями EC2-інстансів ОДНОЧАСНО через NFS-протокол — типово для контент-серверів, спільних домашніх директорій.
  • Автоматично масштабується (не треба вказувати розмір заздалегідь), працює в КІЛЬКОХ AZ одночасно (multi-AZ за дизайном).
  • Дорожчий за EBS за GB, але має storage classes для оптимізації: Standard, Infrequent Access (IA), і One Zone (дешевше, лише 1 AZ).
  • Сумісний лише з Linux-інстансами (не Windows — там використовується FSx for Windows File Server).
ЗАПАМ'ЯТАЙ'Кільком EC2-інстансам у різних AZ потрібен спільний доступ до одних і тих самих файлів' → EFS (не EBS, який прив'язаний до одного інстансу і однієї AZ).
2. EFS, FSx & Instance Store

Amazon FSx — сімейство спеціалізованих файлових систем

Коли потрібен конкретний протокол/технологія

Варіант FSxДля чого
FSx for Windows File ServerSMB-протокол, інтеграція з Active Directory — для Windows-застосунків, що потребують спільних мережевих дисків
FSx for LustreHigh-Performance Computing (HPC), ML-тренування — надшвидкий паралельний доступ до великих датасетів, часто інтегрований з S3
FSx for NetApp ONTAP / OpenZFSМіграція існуючих NetApp/ZFS-навантажень в AWS без зміни застосунку
EXAM TIP'Потрібна Windows-сумісна спільна файлова система з інтеграцією AD' → FSx for Windows, а не EFS (EFS = тільки Linux/NFS).
2. EFS, FSx & Instance Store

Дерево рішень: EFS vs FSx-варіанти

Швидкий алгоритм вибору за протоколом

  • Потрібен НАПІВ NFS + Linux-only → EFS.
  • Потрібен САМЕ SMB-протокол (Windows) → FSx for Windows File Server.
  • Потрібен HPC/ML з надвисоким паралельним доступом, часто пов'язаний з S3 → FSx for Lustre.
  • Потрібні ОБИДВА протоколи ОДНОЧАСНО (і SMB, і NFS до тих самих даних) → FSx for NetApp ONTAP — ЄДИНИЙ варіант, що підтримує обидва протоколи водночас.
EXAM TIPПастка практичних тестів: 'потрібен доступ і через SMB, і через NFS до одних даних' — EFS відпадає (тільки NFS), FSx for Windows відпадає (тільки SMB) → залишається лише ONTAP.
2. EFS, FSx & Instance Store

EC2 Instance Store

Найшвидший, але ефемерний диск

  • Фізично прикріплений до хосту NVMe SSD — найвища продуктивність (IOPS/throughput) з усіх варіантів EC2-сховища.
  • Дані ПОВНІСТЮ втрачаються при Stop, Terminate, або збої хоста (ephemeral storage) — на відміну від EBS.
  • Ідеально для: тимчасового кешу, буферів, тимчасових даних обробки — НІКОЛИ для критичних/persistent даних.
EXAM TIPInstance Store найшвидший, але 'одноразовий' — типова пастка: 'потрібна максимальна продуктивність диску' НЕ означає автоматично Instance Store, якщо дані повинні зберігатись.

Розділ 3

Snow Family, Storage Gateway, DataSync

Перенесення даних between on-premises та AWS

Snow Family

Офлайн-перенесення величезних обсягів даних

  • Проблема, яку вирішуєперенести петабайти даних через звичайний інтернет-канал може зайняти МІСЯЦІ — фізична доставка пристрою швидша.
  • Snowconeмаленький, портативний (для обмежених просторів/edge locations), до ~8-14 TB.
  • Snowball Edgeваліза-сервер з дисками (~80 TB) — може навіть виконувати обчислення (Lambda) на місці, до пересилки в AWS.
  • Snowmobileцілий вантажний контейнер на трейлері (до 100 PB) — для НАЙБІЛЬШИХ дата-центрів, що переїжджають в хмару.
EXAM TIPПравило вибору 'на око': чим більший обсяг даних і повільніший інтернет-канал — тим доречніший фізичний Snow-пристрій замість передачі через мережу.
3. Snow Family, Storage Gateway & DataSync

AWS Storage Gateway

Міст між on-premises і AWS storage

Тип Storage GatewayЩо робить
File Gatewayнадає NFS/SMB доступ локально, а файли зберігає як об'єкти в S3 (з локальним кешем 'гарячих' файлів)
Volume Gateway (Cached)локальний iSCSI том з кешем гарячих даних локально, повна копія — в S3 (як EBS snapshots)

ЗАПАМ'ЯТАЙ'Потрібно поступово мігрувати on-premises застосунок на S3-сховище, зберігаючи локальний файловий доступ' → File Gateway.
3. Snow Family, Storage Gateway & DataSync

AWS DataSync

Автоматизоване, швидке перенесення файлів у мережі

  • На відміну від Snow Family (офлайн, фізична доставка), DataSync переносить дані ОНЛАЙН через мережу — швидше за звичайне копіювання завдяки паралелізації і оптимізації протоколу.
  • Типове застосування: одноразова міграція NFS/SMB файлових серверів в S3/EFS/FSx, або регулярна повторювана синхронізація (replication) між on-premises і AWS.
  • Автоматично перевіряє цілісність даних (integrity verification) і шифрує трафік.
EXAM TIP'Потрібна ПОВТОРЮВАНА, автоматизована синхронізація файлів між локальним NFS-сервером і AWS' → DataSync, а не разова Snowball-доставка.
3. Snow Family, Storage Gateway & DataSync

AWS Transfer Family

Керований SFTP/FTPS/FTP напряму в S3 або EFS

  • Проблема: у багатьох компаній-партнерів вже є ІСНУЮЧІ скрипти й процеси, що завантажують файли через SFTP/FTPS — переписувати їх на 'сучасний' спосіб (API, DataSync) дорого і ризиковано.
  • Transfer Family дає керований SFTP/FTPS/FTP-сервер, за яким ховається S3 або EFS — партнер підключається ЗВИЧНИМ способом (той самий FTP-клієнт, ті самі скрипти), а файл фізично одразу потрапляє в S3/EFS.
  • Це 'міст сумісності' для legacy-протоколів, а не заміна DataSync (яка призначена для масової синхронізації, а не для прийому файлів від зовнішніх партнерів через стандартний протокол).
ЗАПАМ'ЯТАЙ'Партнер надсилає файли через SFTP, і ми не можемо змусити його змінити процес' → AWS Transfer Family, а не намагання перевести партнера на API/DataSync.

Підсумок: Storage Extras одним поглядом

  • EBS: диск для ОДНОГО інстансу, прив'язаний до AZ. AMI = шаблон (ОС + EBS snapshots) для запуску нових інстансів
  • EFS: спільний NFS для БАГАТЬОХ Linux-інстансів, multi-AZ. FSx: спеціалізовані ФС (Windows/Lustre/NetApp)
  • Instance Store: найшвидший, але ephemeral — тільки для тимчасових даних
  • Snow Family (офлайн, петабайти) vs DataSync (онлайн, регулярна синхронізація) vs Storage Gateway (гібридний постійний міст)

Ключ до цього розділу — швидко співставляти сценарій ('один інстанс' / 'багато інстансів' / 'офлайн перенесення' / 'гібридний доступ') з правильним сервісом.
