Розділ 1

Athena та Glue

SQL-запити напряму до файлів у S3, без бази даних

Amazon Athena

Query engine 'serverless' для S3

  • Уяви, що в тебе є мільйони файлів (CSV, JSON, Parquet) у S3, і ти хочеш просто написати SQL-запит, не піднімаючи жодного сервера чи бази даних.
  • Athena читає дані НАПРЯМУ з S3 (не копіюючи їх нікуди) і виконує стандартний SQL — платиш лише за обсяг ЗІСКАНОВАНИХ даних (не за час роботи сервера).
  • Типове застосування: аналіз логів (напр. VPC Flow Logs, ALB access logs, CloudTrail logs), ad-hoc аналітика без потреби у постійній інфраструктурі.
ЗАПАМ'ЯТАЙ'Потрібно швидко проаналізувати логи, що лежать в S3, без розгортання БД' → Athena. Ключове слово: 'serverless SQL напряму по S3'.
1. Athena, Glue & Data Lake

AWS Glue

ETL + каталог метаданих для всього озера даних

  • Glue Crawlerавтоматично 'сканує' дані в S3 і визначає схему (структуру стовпців/типів) — записує в Glue Data Catalog.
  • Glue Data Catalogцентралізований 'каталог метаданих' — Athena, Redshift Spectrum, EMR використовують САМЕ його, щоб знати структуру даних у S3.
  • Glue ETL Jobsсерверless Apache Spark-завдання для трансформації даних (напр. CSV → Parquet, очищення, об'єднання джерел) без керування кластером.
  • Glue DataBrewпроблема: написання Spark-коду для очищення 'брудних' даних (пропуски, дублікати, неправильний формат) вимагає інженера. DataBrew дає ВІЗУАЛЬНИЙ, no-code інтерфейс — аналітик БЕЗ навичок програмування сам 'малює' кроки трансформації (прибрати пропуски, розділити колонку) і одразу бачить прев'ю результату, плюс автоматичний профіль якості даних.
EXAM TIPAthena БЕЗ Glue Data Catalog не знає структури файлів у S3 — Crawler + Catalog зазвичай йдуть ПЕРЕД тим, як можна робити SQL-запити через Athena. DataBrew — це 'Glue ETL для не-програмістів', не заміна, а альтернативний інтерфейс для того самого завдання.
1. Athena, Glue & Data Lake

AWS Lake Formation

Централізований контроль доступу до Data Lake

  • Проблема: у Data Lake (S3 + Glue Catalog) різні команди мають різні права доступу — 'відділ продажів може бачити лише свої таблиці, аналітики — тільки знеособлені колонки'. Керувати цим через окремі S3 bucket policy для кожної комбінації команда/таблиця/колонка — нереально складно і крихко.
  • Lake Formation дає ЄДИНИЙ централізований шар контролю доступу НАД Glue Data Catalog — можна дозволяти доступ на рівні бази, ТАБЛИЦІ, і навіть ОКРЕМОЇ КОЛОНКИ чи РЯДКА (row/column-level security), і ці права одразу застосовуються, коли хтось звертається через Athena/Redshift Spectrum/EMR.
  • Blueprints — готові шаблони для швидкого імпорту даних із зовнішніх джерел (RDS, on-premises БД) прямо в organizовану Data Lake структуру.
ЗАПАМ'ЯТАЙ'Потрібен контроль доступу на рівні окремих колонок/рядків таблиці в Data Lake, який діє однаково для Athena, Redshift Spectrum і EMR' → AWS Lake Formation, а не окремі IAM/S3 policy для кожного сервісу.

Розділ 2

Redshift, OpenSearch, EMR

Коли одного S3 + Athena замало

Amazon Redshift

Data Warehouse для складної бізнес-аналітики

  • На відміну від Athena (запити НАПРЯМУ по S3, без інфраструктури), Redshift — це ПОВНОЦІННИЙ кластер бази даних, куди дані СПОЧАТКУ завантажують (ETL/ELT).
  • Оптимізований для СКЛАДНИХ аналітичних запитів з JOIN по мільярдах рядків (OLAP), на відміну від RDS (OLTP — багато маленьких транзакцій).
  • Redshift Spectrumзвичайний Redshift-запит працює лише з даними, які ти ЗАВАНТАЖИВ у кластер. Spectrum розширює це: Redshift-запит (SQL) може звертатись НАПРЯМУ до файлів у S3 (через Glue Data Catalog), не копіюючи їх у кластер — окремий, зовнішній обчислювальний шар Spectrum сканує S3 і повертає результат так, ніби це звичайна таблиця Redshift. Дозволяє поєднати 'гарячі' дані в кластері з 'холодним' архівом у S3 в ОДНОМУ запиті.
  • Redshift MLдозволяє тренувати і викликати ML-модель ПРЯМО з SQL-запиту (CREATE MODEL) — не треба експортувати дані в окремий ML-сервіс (SageMaker) і писати Python-код; результат передбачення повертається як звичайний стовпець у SQL SELECT.
EXAM TIP'Складна бізнес-аналітика (BI), що вимагає JOIN багатьох великих таблиць, регулярні dashboard-звіти' → Redshift, а не Athena (Athena для 'разових' SQL-запитів по файлах).
2. Redshift, OpenSearch & EMR

Amazon OpenSearch (ex: ElasticSearch)

Пошук і аналіз за межами SQL

  • Уяви пошук слова в паперовій книзі: можна гортати сторінку за сторінкою (повільно, як SQL LIKE '%слово%' — сканує КОЖЕН рядок), а можна відкрити АЛФАВІТНИЙ ПОКАЖЧИК в кінці книги, що одразу каже, на яких сторінках зустрічається слово.
  • OpenSearch заздалегідь будує саме такий 'покажчик' (inverted index): для кожного слова зберігає список документів, де воно є. Тому пошук за словом — миттєвий, незалежно від обсягу даних, на відміну від послідовного сканування файлів (як робить Athena).
  • Типове застосування: пошук по каталогу товарів (e-commerce), аналіз і візуалізація логів застосунків (аналог 'ELK stack' але керований AWS) — саме там, де важлива швидкість повнотекстового пошуку, а не складні SQL JOIN.
ЗАПАМ'ЯТАЙAthena сканує файли КОЖЕН РАЗ заново (добре для рідкісних ad-hoc запитів). OpenSearch будує індекс ЗАЗДАЛЕГІДЬ (добре, коли той самий пошук повторюється тисячі разів на секунду).
2. Redshift, OpenSearch & EMR

Amazon EMR

Elastic MapReduce — керований Hadoop/Spark-кластер

  • Для дуже великих обсягів даних, що вимагають РОЗПОДІЛЕНОЇ обробки (Hadoop, Spark, Hive, Presto) — коли Athena/Glue вже недостатньо гнучкі для складної кастомної логіки.
  • AWS керує кластером (provisioning, patching), але ти сам пишеш і контролюєш Big Data-завдання (на відміну від Glue, де AWS абстрагує все за тебе).
  • Типове застосування: масштабна трансформація/аналіз петабайтів даних, машинне навчання на великих датасетах, обробка логів у величезних масштабах.
ЗАПАМ'ЯТАЙСпрощена ієрархія складності: Athena (найпростіше, SQL по S3) → Glue (керовані ETL-джоби) → EMR (повний контроль над Hadoop/Spark-кластером, найбільша гнучкість і складність).

Розділ 3

QuickSight та типовий Big Data Pipeline

Візуалізація і збирання всього докупи

Amazon QuickSight

BI-дашборди без встановлення софту

  • Serverless business intelligence інструмент — будуєш інтерактивні дашборди й візуалізації, підключаючись до Redshift, Athena, RDS, S3 та інших джерел.
  • SPICEуяви, що 100 менеджерів одночасно відкрили той самий дашборд — БЕЗ SPICE кожне відкриття дашборду означало б новий важкий запит до Redshift/Athena (повільно, і джерело 'задихається' від навантаження). SPICE один раз завантажує потрібні дані в швидку оперативну пам'ять QuickSight, і всі 100 менеджерів отримують відповідь з ЦІЄЇ копії — джерело даних більше не чіпається.
  • Типове застосування: показати керівництву dashboard з бізнес-метриками, не вимагаючи від них SQL-навичок.
3. QuickSight та Big Data Pipeline

Типовий Big Data Ingestion Pipeline

Як усе поєднується докупи

  • 1. Збір: Kinesis Data Streams/Firehose приймають дані в реальному часі (логи, кліки, IoT) → складають у S3 (data lake).
  • 2. Каталогізація: Glue Crawler сканує S3 і будує схему в Glue Data Catalog.
  • 3. Трансформація: Glue ETL Jobs (або EMR для складнішого) очищають/перетворюють дані.
  • 4. Аналіз: Athena для разових SQL-запитів, Redshift для складної BI-аналітики, OpenSearch для пошуку/логів.
  • 5. Візуалізація: QuickSight будує дашборди для бізнес-користувачів.
ЗАПАМ'ЯТАЙЦе один із найпоширеніших 'end-to-end' архітектурних сценаріїв на іспиті — уміння розпізнати КОЖЕН крок і правильний сервіс для нього дуже цінується.

3. QuickSight та Big Data Pipeline

Підсумок: Data & Analytics одним поглядом

  • Athena: serverless SQL напряму по S3, платиш за обсяг сканованих даних
  • Glue: Crawler (визначає схему) + Data Catalog (метадані) + ETL Jobs (трансформація)
  • Redshift: повноцінний Data Warehouse для складної BI-аналітики (OLAP, JOIN мільярдів рядків)
  • OpenSearch: повнотекстовий пошук і аналіз логів. EMR: керований Hadoop/Spark для найскладніших Big Data задач
  • QuickSight: BI-дашборди зі SPICE-кешем. Типовий pipeline: Kinesis → S3 → Glue → Athena/Redshift → QuickSight

На SAA-рівні достатньо впевнено співставляти сценарій із правильним сервісом — глибокі технічні деталі кожного інструменту лишаються для Data Analytics спеціалізації.
