Розділ 1

AWS CloudFormation

Infrastructure as Code

Що таке CloudFormation? (аналогія)

Кулінарний рецепт замість готування 'на око'

  • Уяви, що замість того, щоб щоразу вручну клікати в консолі AWS (створити VPC, потім EC2, потім SG...), ти пишеш ОДИН текстовий 'рецепт' (YAML/JSON template), який описує ВСЮ інфраструктуру.
  • CloudFormation читає цей template і сам створює/оновлює/видаляє ВСІ описані ресурси в правильному порядку, з урахуванням залежностей між ними.
  • Stack — це 'набір ресурсів', створений з одного template — можна видалити ВЕСЬ stack одним кліком, і CloudFormation акуратно приберe все, що сам створив.
  • Переваги: відтворюваність (той самий template = ідентична інфраструктура щоразу), версійність (template зберігається в git), автоматизація (без ручних кліків).
EXAM TIP'Потрібно гарантовано відтворити ІДЕНТИЧНУ інфраструктуру в кількох середовищах (dev/staging/prod) без ручних кліків' → CloudFormation.
1. CloudFormation

CloudFormation Service Role

Хто саме створює ресурси

  • За замовчуванням CloudFormation діє від імені ТОГО, хто запустив deployment (з його IAM-правами).
  • Service Role дозволяє віддати CloudFormation ОКРЕМУ IAM-роль з чітко визначеними правами — навіть якщо у користувача, що запускає stack, менше прав, ніж потрібно для створення ресурсів.
  • Це дозволяє розділити 'хто МОЖЕ запустити deployment' від 'що САМЕ дозволено СТВОРИТИ' — принцип найменших привілеїв.
EXAM TIP'Розробник повинен мати можливість розгортати CloudFormation stack, але НЕ мати прямих прав створювати IAM-ролі чи VPC' → CloudFormation Service Role з ширшими правами, ніж у самого розробника.

SSM Session Manager, SSM Run Command, Trusted Advisor

Керування інстансами без SSH і безкоштовний аудит

SSM Session Manager

SSH/RDP БЕЗ відкритих портів і bastion host

  • Замість того, щоб відкривати порт 22 (SSH) чи 3389 (RDP) і турбуватись про bastion host, Session Manager дає доступ до shell інстансу ЧЕРЕЗ AWS API — інстанс може бути в ПРИВАТНІЙ підмережі БЕЗ жодного вхідного порту, відкритого для SSH/RDP.
  • Вимагає лише встановленого SSM Agent на інстансі й відповідної IAM-ролі — жодних Security Group правил для SSH/RDP не потрібно.
  • Усі сесії логуються централізовано (аудит хто, коли, що робив у сесії) — значно безпечніше за звичайний SSH.
ЗАПАМ'ЯТАЙ'Потрібен доступ до EC2 у приватній підмережі БЕЗ bastion host і БЕЗ відкритого порту SSH' → SSM Session Manager — часта 'найбезпечніша' відповідь на іспиті.

2. Systems Manager (SSM) & Trusted Advisor

AWS Trusted Advisor

Безкоштовний 'аудитор найкращих практик'

  • Автоматично аналізує твій акаунт за 5 категоріями: Cost Optimization, Performance, Security, Fault Tolerance, Service Limits.
  • Базові перевірки безкоштовні для всіх; повний набір перевірок доступний з Business/Enterprise Support планом.
  • Типові знахідки: невикористані Elastic IP (Cost), S3-бакети з публічним доступом (Security), відсутність Multi-AZ (Fault Tolerance).
EXAM TIP'Потрібно швидко перевірити акаунт на типові помилки конфігурації без глибокого аудиту вручну' → Trusted Advisor.

Різне, але важливе для повноти картини

AWS Cost Explorer, Budgets, Compute Optimizer

Три різні інструменти контролю витрат — не взаємозамінні

  • Cost Explorerвізуалізує й аналізує ІСТОРИЧНІ витрати AWS у часі, з фільтрами за сервісом/тегом/акаунтом — дивишся 'що вже витрачено', базовий інструмент FinOps.
  • AWS Budgetsна відміну від Cost Explorer (пасивний перегляд), Budgets АКТИВНО стежить за заданим лімітом і сповіщає (або навіть автоматично зупиняє ресурси через Budgets Actions), коли витрати чи ПРОГНОЗ витрат наближаються до порогу — включно з окремим типом бюджету для відстеження ПОКРИТТЯ Savings Plans.
  • AWS Compute Optimizerаналізує РЕАЛЬНЕ використання (CPU/RAM/мережа) твоїх EC2/Lambda/EBS і рекомендує 'правильний розмір' (rightsizing) — якщо інстанс постійно завантажений на 5%, порадить менший і дешевший тип.
  • Cost Anomaly Detectionавтоматично (через ML) виявляє НЕЗВИЧНІ сплески витрат і сповіщає — не треба вручну щодня переглядати графіки.
EXAM TIPПастка: жоден з цих інструментів не РОБИТЬ дій за тебе автоматично (крім Budgets Actions) — Trusted Advisor і Compute Optimizer лише РЕКОМЕНДУЮТЬ, вони не перезапускають/не вимикають ресурси самі. 'Потрібно автоматично зупинити ресурс при перевищенні бюджету' → саме Budgets Actions, а не просто Cost Explorer.
3. Cost Explorer, Outposts, Batch, Amplify

Savings Plans — які саме навантаження вони покривають

Не універсальна знижка на 'все підряд'

  • Compute Savings Plansнайгнучкіші — покривають EC2 (будь-яка family/OS/регіон) + Fargate + Lambda одночасно.
  • EC2 Instance Savings Plansнайбільша знижка, але прив'язані до КОНКРЕТНОЇ instance family в конкретному регіоні — НЕ покривають Fargate чи Lambda.
  • SageMaker Savings Plansокремий тип САМЕ для SageMaker — Compute/EC2 Instance Savings Plans його НЕ покривають.
EXAM TIPПастка: 'у нас є EC2 Instance Savings Plan, і ми думали, що він також покриє наш Fargate' — ЄС2 Instance SP НЕ поширюється на Fargate/Lambda/SageMaker, для цього потрібен саме Compute Savings Plan (або окремий SageMaker SP).
3. Cost Explorer, Outposts, Batch, Amplify

AWS Outposts

AWS 'залізо' у ТВОЄМУ власному дата-центрі

  • Фізичне обладнання AWS, яке встановлюється у ТВОЄМУ on-premises дата-центрі — та сама API/консоль AWS, але 'залізо' стоїть локально у тебе.
  • Для застосунків, яким за законом/латентністю ОБОВ'ЯЗКОВО потрібно лишатись on-premises (напр. дуже низька latency до локального обладнання, або регуляторні вимоги 'дані не залишають будівлю'), але хочеться керувати тим самим AWS-інструментарієм.
EXAM TIP'Потрібна AWS-інфраструктура, але дані ЮРИДИЧНО НЕ МОЖУТЬ покидати конкретний дата-центр' → Outposts.
3. Cost Explorer, Outposts, Batch, Amplify

AWS Batch та AWS Amplify

Дві протилежні за призначенням, але часті назви

  • AWS Batchкерує запуском batch-обчислень (не веб-застосунок, а 'порахувати й завершитись') на EC2/Fargate — сам вирішує, скільки й яких інстансів підняти для черги завдань, оптимізуючи вартість (може використовувати Spot).
  • AWS Amplifyплатформа для швидкої розробки й розгортання full-stack веб/мобільних застосунків (frontend + backend + CI/CD) — популярна для стартапів і швидких прототипів.
EXAM TIPBatch — для 'порахувати і забути' задач (обробка відео, наукові розрахунки). Amplify — для 'швидко задеплоїти застосунок' (протилежний кінець спектра складності).
3. Cost Explorer, Outposts, Batch, Amplify

AWS Elastic Beanstalk

'Завантажив код — отримав робочий застосунок' PaaS

  • Проблема: розгорнути звичайний веб-застосунок 'правильно' вручну означає самому налаштувати EC2, ASG, ALB, Security Groups, моніторинг — багато однакової рутинної роботи для кожного нового проєкту.
  • Elastic Beanstalk бере твій код (напр. .zip з Java/Node/Python/.NET застосунком) і АВТОМАТИЧНО створює й налаштовує всю цю інфраструктуру (EC2/ASG/ALB) за тебе, за best-practice дефолтами.
  • Ти НЕ втрачаєш доступу до цих ресурсів — можеш зайти й донастроїти EC2/ASG вручну, якщо треба (на відміну від повністю serverless Lambda, де 'сервера' взагалі немає).
ЗАПАМ'ЯТАЙ'Потрібно швидко розгорнути типовий веб-застосунок (EC2+ALB+ASG) без ручного налаштування кожного компонента' → Elastic Beanstalk. Це PaaS, проміжна точка між 'повний контроль вручну' (сам EC2/ALB/ASG) і 'взагалі без серверів' (Lambda).

Підсумок: Other Services одним поглядом

  • CloudFormation: Infrastructure as Code, Stack = набір ресурсів з одного template, Service Role для розділення прав
  • SSM Session Manager: SSH/RDP без відкритих портів і bastion host — часта 'найбезпечніша' відповідь
  • Trusted Advisor: безкоштовний аудит за 5 категоріями (Cost/Performance/Security/Fault Tolerance/Limits)
  • Cost Explorer + Anomaly Detection (контроль витрат), Outposts (AWS on-premises), Batch (batch-обчислення), Amplify (швидкий full-stack деплой)

Цей розділ рідко дає багато питань, але кожен сервіс тут має 1-2 дуже впізнавані 'сигнальні слова' в сценарії — навчись їх розпізнавати.
