Еволюція архітектури: 3 кейси

Як мислить Solutions Architect — від простого до production-ready

Кейс 1: Stateless-застосунок (WhatIsTheTime.com)

Шлях від одного EC2 до відмовостійкої системи

  • Крок 1: один публічний EC2 з Elastic IP.Просто, але єдина точка відмови (SPOF) і downtime при апгрейді.
  • Крок 2: вертикальне масштабування (більший instance type).Все ще downtime під час апгрейду, все ще SPOF.
  • Крок 3: горизонтальне масштабування — кілька EC2 без Elastic IP, Route 53 A-record.Проблема: якщо інстанс зникає, DNS TTL (1 год) все ще вказує на мертву IP.
  • Крок 4: додаємо Load Balancer.ELB абстрагує список живих інстансів — DNS вказує на ELB, а не на конкретні EC2. Це і є фінальна production-ready форма для stateless-застосунку.
EXAM TIPЯкщо в сценарії згадують "downtime при масштабуванні" чи "мертві DNS-записи після видалення інстансу" — відповідь майже завжди ELB + ASG, а не ручне управління Route 53.

Кейс 2: Stateful-застосунок (MyClothes.com)

Проблема сесій за Load Balancer

  • Проблема: користувач логіниться на Instance A, наступний запит ELB спрямовує на Instance B — сесія "загублена".
  • Погане рішення: Sticky Sessions (ELB завжди спрямовує того ж юзера на той самий інстанс).Працює, але нерівномірне навантаження і втрата сесії при падінні конкретного інстансу.
  • Правильне рішення: винести стан (сесії) ЗА МЕЖІ інстансу — в ElastiCache (Redis/Memcached) або DynamoDB.Тепер будь-який інстанс може обслужити будь-якого юзера — справжня stateless-архітектура на рівні compute.
EXAM TIP"Sticky sessions" в сценарії — це майже завжди СИГНАЛ проблеми, яку правильна відповідь вирішує через зовнішнє сховище сесій (ElastiCache/DynamoDB), а не через "увімкнути Sticky Sessions".

Кейс 3: Спільне сховище (MyWordPress.com)

EBS vs EFS для розподілених застосунків

  • Проблема: юзер завантажує картинку на Instance A, інший юзер хоче побачити її через Instance B — але картинка лежить тільки на EBS-диску Instance A.
  • EBS — прив'язаний до ОДНОГО EC2 в ОДНІЙ AZ.Ідеально для single-instance застосунків, НЕ підходить для розподілених.
  • EFS — мережева файлова система, монтується одночасно на БАГАТО EC2 в РІЗНИХ AZ.Розв'язує проблему спільного доступу до файлів для горизонтально масштабованого застосунку.
ЗАПАМ'ЯТАЙAurora (Multi-AZ + Read Replicas) для БД + EFS для спільних файлів + ElastiCache для сесій = класична "правильна" розподілена архітектура на іспиті.

Розділ 2

AWS Elastic Beanstalk

Developer-centric спосіб деплою — PaaS поверх EC2/ASG/ELB/RDS

Що таке Elastic Beanstalk?

Проблема, яку він вирішує

  • Розробники хочуть, щоб їхній код просто запрацював — без ручного налаштування EC2/ASG/ELB/RDS кожного разу.
  • Beanstalk — керований сервіс: автоматично налаштовує capacity provisioning, load balancing, scaling, health monitoring.
  • Розробник відповідає ТІЛЬКИ за код застосунку — решту бере на себе Beanstalk.
  • Сам Beanstalk безкоштовний — платиш лише за underlying-ресурси (EC2, RDS тощо).
  • Все ще маєш ПОВНИЙ контроль над конфігурацією, якщо потрібно щось налаштувати вручну.
EXAM TIPBeanstalk НЕ приховує інфраструктуру — це "developer view" НАД тими самими EC2/ASG/ELB, які ти й так знаєш. Не плутай з повністю serverless Lambda.
2. Elastic Beanstalk

Компоненти та Web/Worker Tier

Application → Version → Environment

  • Applicationколекція компонентів Beanstalk (environments, versions, configurations).
  • Application Versionконкретна ітерація коду застосунку.
  • Environmentнабір AWS-ресурсів, що виконують ОДНУ версію застосунку одночасно. Можна мати кілька середовищ (dev/test/prod).
  • Web Server Tierстандартний ALB + ASG для обробки HTTP-запитів.
  • Worker TierASG, що витягує повідомлення з SQS — для фонової/асинхронної обробки, масштабується за кількістю повідомлень у черзі.
EXAM TIPWeb Tier може НАПРЯМУ слати повідомлення у SQS чергу Worker Tier — класичний decoupling-патерн (той самий принцип, що й SQS/SNS у Messaging-деку).

AWS CloudFormation

Infrastructure as Code — декларативний опис усієї інфраструктури

Що таке CloudFormation і навіщо

Декларативний, не процедурний підхід

  • В шаблоні ти ОПИСУЄШ бажаний стан ("хочу 2 EC2, security group, S3 bucket, load balancer") — CloudFormation сам створює все у правильному порядку.
  • Infrastructure as Codeжодних ручних змін через консоль — усі зміни проходять через код і код-рев'ю.
  • Cost-перевагикожен ресурс у стеку тегується автоматично — легко бачити вартість стеку. Можна оцінити вартість ЗАЗДАЛЕГІДЬ по шаблону. Dev-стрателгія: автоматично видаляти стек о 17:00 і відтворювати о 8:00 — економія.
  • Продуктивністьможна знищити і відтворити всю інфраструктуру миттєво. Автоматична генерація діаграми зі структури шаблону.
EXAM TIP"Автоматизоване видалення dev-середовища вночі для економії" — класичний CloudFormation exam-сценарій для Cost Optimization домену.
3. CloudFormation

CloudFormation Service Role

Принцип найменших привілеїв для деплою

  • IAM Role, яка дозволяє CloudFormation створювати/оновлювати/видаляти ресурси стеку ВІД СВОГО ІМЕНІ.
  • Use case: даєш юзеру право створити/оновити стек, НЕ даючи йому прямих прав на самі ресурси всередині (EC2, S3 тощо).
  • Юзер повинен мати `iam:PassRole` — щоб "передати" цю роль CloudFormation.
EXAM TIPЦе той самий принцип least privilege, що й Permission Boundaries з Advanced Identity — розділяй "хто може ЗАПУСТИТИ деплой" від "які права МАЄ сам деплой".

Розділ 4

Cost Optimization Tools

Cost Explorer, Savings Plans, Anomaly Detection — окремий домен іспиту (20%)

Cost Explorer & AWS Cost Anomaly Detection

Бачити витрати ДО того, як вони стали проблемою

  • Cost Explorerвізуалізує й аналізує витрати за часом — по акаунтах, по місяцях/годинах, до рівня конкретного ресурсу.
  • Допомагає обрати оптимальний Savings Plan (альтернатива Reserved Instances з більшою гнучкістю по instance family/region).
  • Прогнозує використання на 18 місяців наперед на основі історії.
  • Cost Anomaly DetectionML автоматично вчиться на твоїх історичних витратах і виявляє незвичні сплески БЕЗ ручного налаштування порогів.
  • Моніторить по сервісах, member accounts, cost allocation tags — сповіщає через SNS з root-cause аналізом.
EXAM TIP"Виявити незвичний сплеск витрат автоматично, без ручних порогів" → Cost Anomaly Detection (ML). "Проаналізувати й спрогнозувати витрати вручну" → Cost Explorer.

Підсумок: Архітектурні патерни одним поглядом

  • Еволюція: один EC2 → вертикальне масштабування → горизонтальне + ELB → сесії ЗА МЕЖАМИ інстансу (ElastiCache) → спільне сховище (EFS замість EBS)
  • Sticky Sessions — сигнал проблеми, не рішення. Правильне рішення — зовнішнє сховище стану
  • Elastic Beanstalk = developer-view над EC2/ASG/ELB/RDS. Web Tier (HTTP) vs Worker Tier (SQS-based)
  • CloudFormation = Infrastructure as Code, декларативний, Service Role для розділення "хто деплоїть" від "які права має деплой"
  • Cost Explorer (аналіз+прогноз) + Cost Anomaly Detection (ML-виявлення сплесків) — інструменти домену Cost Optimization

Ці кейси показують МИСЛЕННЯ архітектора — саме це тестує іспит через сценарні питання, а не просто знання окремих сервісів.
