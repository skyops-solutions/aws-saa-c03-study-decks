Розділ 1

AWS Organizations

Керування багатьма AWS-акаунтами як одним цілим

Що таке Organizations? (аналогія)

Проста аналогія

  • Уяви велику компанію з окремими "гаманцями" для кожного відділу (Sales, HR, Finance) — але один головний бухгалтер бачить і оплачує все разом.
  • Management Account — головний акаунт, який керує рештою. Member Accounts — підпорядковані акаунти.
  • Consolidated Billing — один платіжний метод на всі акаунти + знижки за обсяг (volume discount на EC2, S3) поширюються на всю організацію разом.
  • Member Account може належати ТІЛЬКИ ОДНІЙ організації одночасно.
  • Organizational Units (OU) — групування акаунтів у дерево: за бізнес-юнітом (Sales/Retail), за середовищем (Dev/Prod/Test), або за проєктом.
EXAM TIPReserved Instances та Savings Plans discounts діляться між усіма акаунтами організації автоматично — це часта причина "чому вигідно" в сценарних питаннях.
1. AWS Organizations

Service Control Policies (SCP)

"Стеля" прав для цілих акаунтів/OU

  • SCP — IAM policy, застосована до OU чи акаунта, що обмежує ЩО МОЖУТЬ юзери/ролі всередині, незалежно від власних IAM-прав.
  • Не діють на Management Account — той завжди має повну владу.
  • Явний Deny в SCP на будь-якому рівні шляху (Root→OU→Account) блокує дію, навіть якщо IAM policy юзера дозволяє.
  • За замовчуванням SCP нічого не дозволяє (як і звичайний IAM) — потрібен явний Allow десь у ланцюжку ВІД root ДО акаунта.
EXAM TIPФормула: Ефективний дозвіл = IAM Policy юзера ПЕРЕТНУТИЙ з SCP організації. Якщо SCP забороняє S3 — навіть AdministratorAccess у юзера не допоможе.

Просунуті можливості IAM

Conditions, Permission Boundaries, Resource-Based Policies

IAM Conditions & Permission Boundaries

Тонший контроль, ніж прості Allow/Deny

  • IAM Conditionsдодаткові умови в policy: aws:SourceIp (з якого IP), aws:RequestedRegion (в якому регіоні), aws:MultiFactorAuthPresent (примусити MFA), ec2:ResourceTag (за тегами ресурсу).
  • Permission Boundaries"стеля" максимальних прав для КОНКРЕТНОГО юзера/ролі (не групи!) — навіть якщо IAM policy дає більше, Boundary все одно обмежить.
  • Use case Permission Boundariesдозволити розробнику самому створювати IAM-політики для себе, але гарантувати, що він НІКОЛИ не зможе зробити себе адміном ("privilege escalation").
EXAM TIPPermission Boundary + IAM Policy = перетин (AND), як і SCP. Формула фінального дозволу завжди "найменше зі всіх обмежень".

Розділ 3

IAM Identity Center & Directory Services

Single Sign-On для всієї організації

AWS IAM Identity Center (колишній SSO)

Один логін — доступ до всього

  • Один логін для: всіх AWS-акаунтів в Organizations + бізнес-застосунків (Salesforce, Box, Microsoft 365) + SAML2.0-застосунків + Windows EC2.
  • Identity providers: вбудоване сховище ідентичностей АБО сторонні (Active Directory, OneLogin, Okta).
  • Permission Setsколекція IAM-політик, призначена юзерам/групам — визначає доступ у кожному акаунті.
  • ABAC (Attribute-Based Access Control)права базуються на атрибутах юзера (cost center, посада) — визнач права один раз, потім міняй лише атрибути.
EXAM TIPIAM Identity Center — це наступник AWS SSO (та сама назва може зустрітись у старіших питаннях). Working across MULTIPLE accounts — головна відмінність від звичайного IAM.

Розділ 4

AWS Control Tower

Автоматизоване управління мультиакаунтним середовищем

Control Tower & Guardrails

Automаtion поверх Organizations

  • Легкий спосіб налаштувати й керувати безпечним, комплаєнтним мультиакаунтним AWS-середовищем "з коробки" (best practices).
  • Control Tower використовує AWS Organizations "під капотом" для створення акаунтів.
  • Preventive Guardrail — через SCP (наприклад, "заборонити регіони поза списком дозволених" на ВСІХ акаунтах разом).
  • Detective Guardrail — через AWS Config (наприклад, "знайти нетеговані ресурси") — може автоматично тригерити Lambda для виправлення (remediation).
EXAM TIPPreventive = блокує ДО того, як дія станеться (SCP). Detective = виявляє ПІСЛЯ того, як дія вже сталась (Config), і може автоматично виправити.

4. AWS Control Tower

Підсумок: Advanced Identity одним поглядом

  • Organizations: Management + Member Accounts, Consolidated Billing, OU-дерево, SCP = "стеля" прав для цілих акаунтів
  • Ефективний дозвіл = перетин IAM Policy ∩ SCP ∩ Permission Boundary — найменше з усіх обмежень завжди перемагає
  • IAM Role (асьюм) vs Resource-Based Policy — два різні шляхи cross-account доступу
  • IAM Identity Center = SSO на всю організацію + бізнес-застосунки; Directory Services = міст до Active Directory
  • Control Tower = автоматизація Organizations + Guardrails (Preventive через SCP, Detective через Config)

Мультиакаунтна тема зростає у вазі з кожною новою версією іспиту — не пропускай SCP-логіку.
