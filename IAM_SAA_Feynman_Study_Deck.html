Розділ 1

IAM: Users, Groups, Policies, Roles

Хто ти і що тобі можна

Що таке IAM? (як для 5-річного)

Аналогія: пропускна система в офісі

  • Уяви офіс з картками-перепустками: кожен співробітник (User) має картку, картки можна групувати за відділом (Group), а правила доступу (Policy) визначають, куди саме можна заходити.
  • IAM = Identity and Access Management — глобальний (не regional) сервіс AWS для керування 'хто може робити що' в акаунті.
  • Root user (обліковий запис, створений при реєстрації) має АБСОЛЮТНО всі права — його НЕ можна обмежити policy, тому AWS рекомендує НЕ використовувати root для щоденної роботи.
  • За замовчуванням новий IAM User не має ЖОДНИХ прав (implicit deny) — доки йому явно не додати policy.
EXAM TIPПерше, що варто зробити з новим AWS-акаунтом: увімкнути MFA на root, створити окремого IAM-адміністратора, і більше НЕ користуватись root-обліковкою.
1. IAM Основи

Users, Groups, Roles — у чому різниця

Найпростіша, але важлива класифікація

  • Userконкретна особа чи застосунок з довготривалими credentials (пароль/access keys).
  • Groupколекція Users — policy, прикріплена до групи, застосовується до ВСІХ її учасників (групи НЕ можна вкладати одна в одну).
  • Roleнабір прав, який можна ТИМЧАСОВО 'приміряти' (assume) — використовується EC2/Lambda/іншими AWS-сервісами, або іншими акаунтами. Немає постійних credentials.
  • PolicyJSON-документ, що описує дозволи (Effect/Action/Resource/Condition).
EXAM TIPРоль (Role) видає ТИМЧАСОВІ credentials через STS (Security Token Service — окремий AWS-сервіс, єдина задача якого — видавати короткострокові тимчасові credentials замість постійних) за замовчуванням на 1 годину. Це найбезпечніший спосіб надати доступ сервісу чи іншому акаунту: навіть якщо ці тимчасові credentials хтось перехопить, вони самі стануть непридатними за годину.

Розділ 2

Policy Evaluation Logic

Як AWS вирішує 'дозволено чи ні'

Порядок оцінки: за замовчуванням Deny

Найважливіший алгоритм на іспиті

  • 1. Явний DENY завжди перемагає — якщо ХОЧ ОДНА застосовна policy каже Deny, це фінальне рішення (незалежно від інших Allow).
  • 2. Якщо явного Deny немає — перевіряється, чи є ХОЧА Б ОДИН явний Allow (у Identity-based АБО Resource-based policy).
  • 3. Якщо немає жодного явного Allow — результат за замовчуванням DENY (implicit deny).
  • SCP (Organizations) і Permissions Boundary діють як 'стеля' — вони не дають прав самі по собі, а лише ОБМЕЖУЮТЬ те, що дозволено нижче.
ЗАПАМ'ЯТАЙФормула для запам'ятовування: 'Explicit Deny > Explicit Allow > Implicit Deny (за замовчуванням)'. SCP/Boundary — це додаткові 'стелі', а не джерела дозволів.
2. Policy Evaluation Logic

Cross-Account доступ

Коли Role потрібна ОБОВ'ЯЗКОВО

  • Щоб дати користувачу з Акаунту A доступ до ресурсу в Акаунті B: створюєш Role в Акаунті B з Trust Policy, що дозволяє Акаунту A 'приміряти' цю роль.
  • Користувач з Акаунту A виконує sts:AssumeRole → отримує тимчасові credentials → діє від імені ролі в Акаунті B.
  • Це набагато безпечніше, ніж створювати окремого IAM User в Акаунті B і ділитись його довготривалими credentials.
EXAM TIP'Компанія A повинна отримати тимчасовий доступ до ресурсів компанії B' — класичний натяк на Cross-Account IAM Role + AssumeRole.
2. Policy Evaluation Logic

Пастки з практичних тестів

Permissions Boundary vs SCP — на чому саме ламаються

  • Permissions Boundary працює ЛИШЕ на User/Roleне можна прикріпити Permissions Boundary до Group. Якщо треба обмежити 'стелю' прав для цілої команди — доведеться ставити Boundary на КОЖНОГО User/Role окремо, або обмежувати через SCP на рівні акаунту.
  • SCP НЕ діє на management account організаціїі не обмежує service-linked roles (спеціальні ролі, які AWS-сервіси створюють самі для себе). Пастка: 'ми поставили SCP, що забороняє все, а адмін management-акаунту все одно все може' — це очікувана поведінка, не баг.
  • Явна відмова від self-escalationIAM policy, прикріплена ПРЯМО до User, може бути змінена/видалена самим цим User (якщо в нього є права iam:PutUserPolicy) — це НЕ захищає від підвищення прав. Permissions Boundary чи SCP, які User не може редагувати сам, — єдиний надійний спосіб капнути максимум прав.
EXAM TIPТипова пастка практичних тестів: 'як гарантовано не дати User підвищити собі права' → відповідь завжди Permissions Boundary або SCP (те, чим User НЕ управляє), ніколи не 'просто IAM policy'.

Розділ 3

Organizations, IAM Identity Center, Directory Services

Керування на рівні багатьох акаунтів

AWS Organizations

Централізоване керування багатьма AWS-акаунтами

  • Що цедозволяє об'єднати кілька AWS-акаунтів в одну структуру (Organizational Units) з єдиним білінгом і централізованими правилами (SCP).
  • Consolidated Billingодин рахунок на всю організацію + об'єднані знижки за обсягом (volume discounts) і Reserved Instance sharing між акаунтами.
  • Best practiceокремі акаунти для prod/dev/security/logging — ізоляція blast radius, а не один 'великий' акаунт на все.
  • Tag Policiesстандартизують теги ресурсів (напр. обов'язковий тег 'CostCenter') на рівні всієї організації.
EXAM TIP'Потрібна ізоляція середовищ і централізований контроль витрат для 20 команд' → AWS Organizations з окремими акаунтами на команду/середовище.
3. IAM Advanced: Organizations, Identity Center, Directory Services

IAM Identity Center (колишній AWS SSO)

Один логін для всіх акаунтів

  • Дозволяє співробітнику залогінитись ОДИН раз і отримати доступ до КІЛЬКОХ AWS-акаунтів і застосунків (напр. Salesforce), без окремих IAM Users у кожному акаунті.
  • Інтегрується із зовнішнім Identity Provider (Active Directory, Okta, Azure AD) через SAML/OIDC.
  • Замінює застарілий патерн 'IAM User в кожному акаунті' на централізоване федероване управління ідентичністю.
ЗАПАМ'ЯТАЙ'Потрібен SSO для десятків AWS-акаунтів організації' → IAM Identity Center, а не створення однакових IAM Users у кожному акаунті окремо.

Підсумок: IAM одним поглядом

  • User (постійні credentials) vs Role (тимчасові, assume) vs Group (колекція Users) — три різні інструменти
  • Policy Evaluation: Explicit Deny > Explicit Allow > Implicit Deny (за замовчуванням) — SCP/Boundary лише обмежують
  • Cross-account доступ = завжди через Role + AssumeRole, ніколи через спільні довготривалі credentials
  • Organizations (SCP, consolidated billing) + IAM Identity Center (SSO) — керування security на рівні багатьох акаунтів

IAM — це 'граматика' security-питань іспиту. Якщо розумієш Policy Evaluation Logic — половина security-питань стає легшою.
