Розділ 1

Amazon S3 Basics

Simple Storage Service — нескінченна шафа для файлів

Що таке S3? (як для 5-річного)

Проста аналогія

  • Уяви величезну камеру схову, де можна покласти БУДЬ-ЯКИЙ файл (документ, фото, відео, бекап) і забрати його з будь-якої точки світу.
  • S3 = object storage: зберігає "об'єкти" (файл + метадані + унікальний ключ), а не файлову систему з папками (папки — це лише візуальна ілюзія в консолі, насправді все — плаский простір ключів).
  • Bucket — це "контейнер" для об'єктів. Класичне (і досі основне для іспиту) правило: ім'я бакета глобально унікальне — на весь AWS, не тільки твій акаунт.
  • Максимальний розмір об'єкта — 5 TB. Для файлів > 5 GB — обов'язково Multipart Upload.
EXAM TIPS3 — це не диск і не файлова система. Це HTTP API (PUT/GET/DELETE) для зберігання об'єктів необмеженого сумарного обсягу.
1. S3 Basics

Ключова структура

Bucket → Object → Key

  • Bucketстворюється в конкретному регіоні; класичний 'general purpose' bucket — ім'я глобально унікальне в межах partition (DNS-сумісне).
  • Objectфайл (0 байт – 5 TB) + метадані (Content-Type, теги, тощо).
  • Keyповний шлях об'єкта, напр. 'photos/2024/cat.png' — саме він і є 'ім'ям файлу'.
  • Version IDякщо увімкнено Versioning — кожен апдейт об'єкта отримує свій ID.
  • 11 nines durability (99.999999999%)S3 реплікує дані в межах ≥3 AZ автоматично.
EXAM TIPDurability (11 nines) ≠ Availability (99.9%-99.99% залежно від storage class). Дані не губляться, але доступ короткочасно може бути недоступний.
1. S3 Basics

Оновлення 2026: не всі bucket-імена глобально унікальні

Свіжа деталь — для реальної роботи, поки що поза класичним іспитом

  • Account Regional Namespaces (з березня 2026)новий, опційний спосіб створювати 'general purpose' бакети у ВЛАСНОМУ зарезервованому просторі імен акаунта+регіону — ім'я більше НЕ повинно бути унікальним у всьому AWS, лише в межах твого акаунта. Такі бакети мають суфікс '-an'.
  • Directory Buckets (S3 Express One Zone)окремий тип бакета для надшвидкого доступу в 1 AZ; ім'я унікальне лише в межах обраної Zone, формат 'base-name--zone-id--x-s3', а НЕ глобально.
  • Класичні 'general purpose' бакетиі далі за замовчуванням існують у СПІЛЬНОМУ глобальному просторі імен — це правило, яке досі варто знати для іспиту SAA-C03.
EXAM TIPSAA-C03 наразі (на 2026 рік) тестує КЛАСИЧНЕ правило 'глобально унікальне ім'я бакета'. Account Regional Namespaces — це дуже свіжа фіча (Mar 2026), тому для іспиту вважай базове правило основним, але знай про цей виняток для реальних проєктів.
1. S3 Basics

Consistency Model

Важлива деталь для сценаріїв

  • З грудня 2020 S3 надає Strong Read-After-Write Consistency для ВСІХ операцій (PUT нового об'єкта, і навіть overwrite PUT/DELETE).
  • Це означає: щойно записав об'єкт — наступний GET одразу поверне нову версію, без затримки на реплікацію.
ЗАПАМ'ЯТАЙДо 2020 S3 мав 'eventual consistency' для overwrite PUT/DELETE — старі матеріали/питання можуть це згадувати, але зараз це вже НЕ так: consistency строга завжди.

S3 Storage Classes

Плати тільки за швидкість доступу, яка тобі реально потрібна

Аналогія

Шафа вдома vs камера схову vs архів на дачі

  • Standard — шафа в кімнаті: миттєвий доступ, найдорожче за GB.
  • Infrequent Access — комора в підвалі: доступ трохи повільніший, дешевше зберігання, але платиш за 'відкривання дверей' (retrieval fee).
  • Glacier — контейнер на складі за містом: дуже дешево зберігати, але треба заздалегідь замовити доставку (retrieval time від хвилин до годин/днів).
EXAM TIPГоловна ідея класів: чим рідше звертаєшся до даних — тим дешевше зберігання, але дорожче/повільніше дістати.

2. Storage Classes

S3 Intelligent-Tiering

Автоматика замість ручного вибору

  • Автоматично переміщує об'єкти між рівнями доступу на основі патернів звернень (без затрат на retrieval і без штрафів за передчасне видалення).
  • Рівні: Frequent Access → Infrequent Access (>30 днів без доступу) → Archive Instant Access (>90 днів) → опційно Deep Archive Access (>180 днів).
  • Невелика місячна плата за моніторинг об'єкта, але економія при непередбачуваних патернах доступу.
ЗАПАМ'ЯТАЙСценарій іспиту: 'патерн доступу до даних невідомий або змінюється' → відповідь майже завжди S3 Intelligent-Tiering.

S3 Versioning, Lifecycle & Replication

Захист від помилок і географічна доступність

Versioning

Аналогія: Google Docs 'історія версій'

  • Коли увімкнено, кожен overwrite чи delete створює НОВУ версію замість втрати старої.
  • Delete насправді додає 'delete marker' (soft delete) — можна відновити, видаливши маркер.
  • Versioning вмикається на рівні bucket, і після ввімкнення його не можна вимкнути — лише 'призупинити' (Suspended).
  • Об'єкти, завантажені ДО ввімкнення versioning, отримують Version ID = 'null'.
EXAM TIPVersioning + MFA Delete = захист навіть від адмінів, які випадково (чи зловмисно) видаляють об'єкти.
3. Versioning & Replication

Lifecycle Rules

Автоматичне 'старіння' даних

  • Transition Actionsперемістити об'єкт в інший клас зберігання через N днів (напр. Standard → IA через 30 днів → Glacier через 90).
  • Expiration Actionsвидалити об'єкт (або стару версію) через N днів.
  • Можна фільтруватиза префіксом ключа або тегами об'єкта.
EXAM TIPТипове поєднання на іспиті: Versioning + Lifecycle, що переносить НЕ-поточні версії в Glacier через 30 днів і видаляє через 365.
3. Versioning & Replication

Пастки правил переходу між класами

Напрямок руху лише 'вниз' — і не миттєво

  • Мінімум 30 днів перед переходом у IA/One Zone-IAспроба налаштувати перехід через 7 днів — завжди неправильна відповідь; AWS фізично не дозволяє переходити швидше.
  • Не можна повернутись 'вгору'не можна зробити Lifecycle-правило, що переносить об'єкт з Intelligent-Tiering НАЗАД у Standard, чи з Glacier назад у Standard-IA — переходи Lifecycle рухаються лише в напрямку 'дешевше й повільніше'.
  • One Zone-IA — тільки в один бік ізольованоне можна перейти з One Zone-IA в Standard-IA чи Intelligent-Tiering (обидва — Multi-AZ за дизайном, тоді як One Zone-IA — свідомо єдина AZ; 'підвищення' надійності таким шляхом не підтримується).
  • S3 Storage Class Analysis рекомендує лише ОДИН перехідStandard → Standard-IA — цей інструмент НІКОЛИ не порадить One Zone-IA чи Glacier (там ризик/затримка занадто специфічні для автоматичної рекомендації).
EXAM TIPЯкщо в питанні Lifecycle Rule описує перехід 'назад' до дешевшого→дорожчого класу або швидше ніж 30 днів у IA — це завжди неправильна відповідь.

S3 Object Lock: Compliance vs Governance

WORM-захист — яка різниця насправді

  • Governance modeзахищає об'єкт від видалення/перезапису для 'звичайних' користувачів, але User З ПРАВОМ s3:BypassGovernanceRetention (напр. адміністратор) може обійти захист і видалити об'єкт достроково.
  • Compliance modeСПРАВЖНІЙ WORM (Write Once Read Many) — об'єкт не може видалити НІХТО, включно з root-акаунтом, доки не сплине retention period. Навіть AWS Support не може це скасувати.
  • Коли якеGovernance — для внутрішніх процесів, де рідко, але потрібно 'екстрене' видалення з дозволу. Compliance — для юридичних/регуляторних вимог (напр. фінансові записи), де 'ніхто не може видалити' — буквальна вимога закону.
EXAM TIPПрактичні тести відрізняють ці два режими саме через 'хто може обійти захист': Governance — привілейований адмін МОЖЕ; Compliance — НІХТО не може, це і є 'справжній' WORM.
3. Versioning & Replication

Replication (CRR / SRR)

Копія бакета в іншому регіоні або тому самому

  • CRR (Cross-Region Replication)копіювання об'єктів в бакет в ІНШОМУ регіоні — для compliance, latency, disaster recovery.
  • SRR (Same-Region Replication)копіювання в бакет ТОГО Ж регіону — для агрегації логів з кількох акаунтів, production/test синхронізації.
  • ВимогиVersioning увімкнено і на джерелі, і на призначенні; потрібен IAM Role з правами.
  • Реплікація НЕ ретроактивнакопіюються тільки НОВІ об'єкти після налаштування (для старих — окремий batch job).
EXAM TIPРеплікація асинхронна (зазвичай <15 хв) і за замовчуванням НЕ реплікує старі об'єкти, наявні до налаштування правила.

S3 Security

Bucket Policy, IAM, ACL, шифрування, presigned URLs

Хто вирішує 'можна чи ні'

IAM Policy vs Bucket Policy vs ACL

  • IAM Policyприкріплюється до IAM user/role — 'що МОЖЕ робити ця людина/сервіс' (identity-based).
  • Bucket Policyприкріплюється до самого бакета (JSON) — 'хто МОЖЕ звертатись до цього бакета' (resource-based), в т.ч. cross-account доступ.
  • ACL (Access Control List)старіший механізм на рівні об'єкта/бакета; AWS рекомендує вимикати ACL і використовувати лише Policy (Object Ownership = Bucket owner enforced).
  • Block Public Accessокремий 'рубильник' на рівні акаунту/бакета — перекриває навіть дозвільні policy, якщо увімкнено.
EXAM TIPСценарій 'зробили bucket policy public, але доступу все одно немає' → перевір Block Public Access на рівні акаунту.

4. S3 Security

Ще важливі механізми

Часто в сценаріях іспиту

  • CORSбраузери за замовчуванням БЛОКУЮТЬ JS-код на сайті domain-A.com від звернення до ресурсів на domain-B.com (Same-Origin Policy — захист від зловмисних сайтів, що тихцем читають чужі дані). Якщо твій сайт на CloudFront/EC2 має JS, що завантажує файли НАПРЯМУ з S3-бакета (іншого 'домену') — браузер заблокує цей запит, доки бакет явно не дозволить це через CORS-конфігурацію.
  • Presigned URLтимчасове посилання з підписом — дає доступ на GET/PUT без розкриття AWS credentials, з терміном дії. Механізм: посилання містить криптографічний підпис, згенерований твоїми credentials наперед — той, хто перейде за посиланням, НЕ бачить і не отримує самі credentials, лише одноразовий тимчасовий доступ, який сплине.
  • MFA Deleteвимагає MFA-код для permanent delete версії об'єкта чи вимкнення versioning — захищає саме від сценарію 'вкрадений пароль адміна' чи 'помилковий клік', бо для РУЙНІВНИХ дій потрібен ще й фізичний токен/телефон адміна.
  • Access Pointsпроблема: якщо 200 різних застосунків звертаються до ОДНОГО спільного бакета, і кожному потрібен ДОСТУП ЛИШЕ до свого префіксу — довелось би тримати одну гігантську, заплутану bucket policy на всіх (яка ще й має ліміт розміру), і будь-яка правка ризикує зламати доступ комусь іншому. Access Point дає кожному застосунку СВОЮ окрему 'точку входу' зі своєю окремою policy й навіть окремим мережевим обмеженням (напр. 'лише з цієї VPC') — зміни для одного застосунку більше не чіпають інших.
  • S3 Multi-Region Access Point (MRAP)один Access Point, який працює одразу через КІЛЬКА бакетів у РІЗНИХ регіонах — застосунок звертається до ОДНОЇ адреси, а MRAP сам маршрутизує запит до найближчої/найшвидшої репліки. Вирішує задачу 'глобальний застосунок повинен писати/читати S3 з мінімальною latency з будь-якої точки світу' без ручного вибору регіону в коді.
  • S3 Bucket Keyпроблема: кожен запит із SSE-KMS шифруванням викликає KMS API (Encrypt/Decrypt) — при мільйонах об'єктів це і повільно, і дорого (платиш за кожен виклик KMS). Bucket Key генерує один короткостроковий 'проміжний' ключ на рівні бакета, яким шифруються МНОЖИНА об'єктів, замість звернення до KMS на КОЖЕН окремий об'єкт — суттєво знижує кількість викликів KMS і вартість.
4. S3 Security

Object Lock: Legal Hold vs Retention Period

Дві незалежні 'печатки' на об'єкті

  • Retention Period (з режимом Governance/Compliance)фіксований ТЕРМІН — 'не можна видалити до дати X' (розглянуто на попередньому слайді).
  • Legal HoldНЕЗАЛЕЖНИЙ від retention period прапорець 'не можна видалити, доки прапорець не знімуть' — БЕЗ конкретної дати закінчення. Типове застосування: судовий позов чи розслідування, де заздалегідь невідомо, скільки часу потрібно зберігати докази. Legal Hold можна додати/зняти в будь-який момент (якщо в тебе є права), незалежно від того, чи є на об'єкті ще й Retention Period.
  • Обидва можуть діяти одночаснооб'єкт видаляється лише тоді, коли І Retention Period сплив, І Legal Hold знятий — вони незалежні одна від одної 'печатки захисту'.
ЗАПАМ'ЯТАЙ'Термін зберігання невідомий заздалегідь, залежить від того, коли завершиться судовий розгляд' → Legal Hold, а не Retention Period (в якого завжди є конкретна дата).
4. S3 Security

S3 Website & CloudFront

Роздача контенту користувачам

  • S3 Static Website Hostingбакет може віддавати HTML напряму по HTTP (не HTTPS) — URL формату bucket-name.s3-website-region.amazonaws.com.
  • CloudFront + S3 (OAC)правильний production-патерн: CloudFront як CDN перед приватним бакетом через Origin Access Control — HTTPS, кешування, бакет лишається приватним.
  • Geo Restriction / Cache InvalidationCloudFront дозволяє обмежити доступ за країною і примусово скинути кеш конкретних шляхів.
ЗАПАМ'ЯТАЙЯкщо в питанні є 'HTTPS' і 'S3 static website' одночасно — правильна відповідь майже завжди CloudFront перед бакетом, а не голий S3 website endpoint (він не підтримує HTTPS).
