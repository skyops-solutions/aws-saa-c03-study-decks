Розділ 1

Amazon CloudWatch

Метрики, логи, алярми — 'як почувається' система

Що таке CloudWatch? (аналогія)

Приладова панель автомобіля

  • Уяви приладову панель у машині: швидкість, рівень пального, температура двигуна — цифри в реальному часі, що показують СТАН системи.
  • CloudWatch Metrics — це такі 'цифри' для AWS-ресурсів: CPU Utilization, Network In/Out, кількість помилок тощо. Більшість сервісів шлють метрики автоматично кожні 5 хв (Detailed Monitoring — щохвилини, за додаткову плату).
  • CloudWatch Logs — збирає ТЕКСТОВІ логи застосунків (через CloudWatch Agent на EC2, або автоматично від Lambda/API Gateway тощо) в одному централізованому місці.
  • CloudWatch Alarms — 'сигналізація': коли метрика перетинає поріг (напр. CPU > 80% протягом 5 хв) — тригерить дію (сповіщення через SNS, Auto Scaling, тощо).
EXAM TIPCloudWatch відповідає на питання 'ЯК ЗАРАЗ почувається моя система?' — це моніторинг продуктивності й здоров'я, а не хто що зробив чи як усе налаштовано.
1. Amazon CloudWatch

CloudWatch Agent та кастомні метрики

Деталі, які часто плутають

  • Стандартні метрики EC2CPU, мережа, диск (лише READ/WRITE операції) — доступні 'з коробки', БЕЗ агента.
  • RAM Usage / MemoryНЕ доступна за замовчуванням! Потрібно встановити CloudWatch Agent на інстанс, щоб надсилати цю кастомну метрику.
  • CloudWatch Agentзбирає системні метрики (RAM, дисковий простір ВСЕРЕДИНІ ОС) і логи з EC2/on-premises серверів.
  • EventBridge (колишній CloudWatch Events)реагує на ПОДІЇ (не метрики) — напр. 'EC2 інстанс змінив стан' або за розкладом (cron) — тригерить Lambda/SNS/Step Functions.
EXAM TIP'Потрібно відстежувати використання RAM на EC2' — класична пастка: RAM НЕ входить у стандартні метрики, потрібен CloudWatch Agent.
1. Amazon CloudWatch

Composite Alarms, EC2 Auto-Recovery, Container Insights & X-Ray

Просунуті фічі спостережуваності

  • Composite Alarmзвичайний Alarm стежить за ОДНІЄЮ метрикою. Якщо потрібно тригерити дію лише коли КІЛЬКА умов співпадають одночасно (напр. 'і CPU високий, І кількість помилок зросла' — а не будь-яке окремо, щоб уникнути помилкових спрацювань) — Composite Alarm об'єднує кілька звичайних Alarms через AND/OR логіку в одне правило.
  • EC2 Auto-Recovery (дія Alarm)CloudWatch Alarm може не просто сповістити, а сам АВТОМАТИЧНО перезапустити 'нездоровий' EC2-інстанс на новому фізичному хості (напр. при апаратному збої) — без втручання людини і без втрати даних/IP (на відміну від Auto Scaling, яке замінює інстанс на НОВИЙ).
  • Container Insights + X-Rayзвичайні CloudWatch метрики бачать 'зовні' (CPU/RAM хоста), але не бачать, що відбувається ВСЕРЕДИНІ контейнерного кластера чи мікросервісної архітектури. Container Insights збирає метрики й логи саме на рівні ECS/EKS (використання ресурсів по кожному Task/Pod). X-Ray йде глибше: трасує ОДИН запит користувача через ВСІ мікросервіси, якими він пройшов, показуючи, ДЕ саме виникла затримка чи помилка в цьому ланцюжку.
ЗАПАМ'ЯТАЙ'Потрібно знайти, який саме мікросервіс у ланцюжку викликів гальмує запит користувача' → X-Ray (distributed tracing), а не звичайні CloudWatch метрики, які бачать лише окремі сервіси ізольовано.

AWS CloudTrail

Хто, що і коли зробив в акаунті

Що таке CloudTrail? (аналогія)

Камера відеоспостереження на кожному API-виклику

  • Уяви камеру, що записує КОЖНОГО, хто заходить у будівлю: хто саме, коли, і що саме зробив (відкрив двері, взяв документ).
  • CloudTrail записує КОЖЕН API-виклик в акаунті AWS: хто (IAM User/Role), звідки (IP), коли, і який саме Action (напр. 'TerminateInstances', 'DeleteBucket').
  • Увімкнений АВТОМАТИЧНО для кожного акаунту (90 днів історії безкоштовно через Event History в консолі); для довшого зберігання і аналізу — налаштовується Trail, що пише логи в S3.
  • Це ІНСТРУМЕНТ АУДИТУ І РОЗСЛІДУВАННЯ — не моніторинг продуктивності (це CloudWatch) і не перевірка конфігурації (це Config).
EXAM TIPCloudTrail відповідає на питання 'ХТО і ЩО зробив?' — класичний сценарій: 'S3 bucket видалили, хто це зробив?' → шукай в CloudTrail.
2. AWS CloudTrail

CloudTrail Insights & EventBridge Integration

Просунуті фічі

  • CloudTrail Insights автоматично виявляє НЕЗВИЧНУ активність API-викликів (напр. різкий сплеск помилок або незвичний обсяг викликів) за допомогою ML.
  • Інтеграція з EventBridge: можна тригерити Lambda/SNS одразу, коли стався ПЕВНИЙ API-виклик (напр. миттєво сповістити, якщо хтось видалив Security Group).
  • Логи CloudTrail можна писати в S3 (для довгострокового зберігання) і CloudWatch Logs (для real-time аналізу/алярмів).
ЗАПАМ'ЯТАЙ'Потрібно миттєво дізнатись, коли хтось вимкнув CloudTrail logging чи змінив security group' → CloudTrail + EventBridge правило на конкретний API call.

Розділ 3

AWS Config

Чи відповідає конфігурація ресурсів правилам

Що таке AWS Config? (аналогія)

Інспектор, що перевіряє 'чи все за регламентом'

  • Уяви інспектора, який регулярно обходить будівлю і перевіряє: 'чи всі двері зачинені за правилами протипожежної безпеки?', і записує КОЖНУ зміну в часі.
  • AWS Config відстежує КОНФІГУРАЦІЮ AWS-ресурсів у часі — напр. 'цей Security Group мав ці правила о 10:00, а о 14:00 хтось додав правило 0.0.0.0/0 на порт 22'.
  • Config Rules — це 'правила регламенту': можна перевіряти автоматично, чи ресурси відповідають політикам (напр. 'усі EBS volumes повинні бути зашифровані', 'жоден S3 bucket не повинен бути публічним').
  • Якщо ресурс порушує правило — Config позначає його NON_COMPLIANT і може навіть автоматично тригерити виправлення (remediation) через SSM Automation.
EXAM TIPConfig відповідає на питання 'ЯК саме НАЛАШТОВАНИЙ ресурс, і чи відповідає це нашим правилам?' — не хто це зробив (CloudTrail) і не як він 'почувається' (CloudWatch).
3. AWS Config

CloudTrail vs CloudWatch vs Config

Фінальне порівняння — часте питання іспиту

СервісНа яке питання відповідаєПриклад
CloudWatch'Як зараз почувається система?' (метрики/логи продуктивності)'CPU на 90% останні 10 хв — тригерни alarm'
CloudTrail'ХТО і ЩО зробив, і КОЛИ?' (аудит дій/API-викликів)'Хто видалив цей S3 bucket вчора о 15:32?'
Config'ЯК НАЛАШТОВАНИЙ ресурс, і чи відповідає правилам?' (конфігурація в часі)'Чи всі наші EBS-томи зашифровані? Коли SG стала публічною?'
ЗАПАМ'ЯТАЙТримай в голові коротку формулу: CloudWatch = продуктивність, CloudTrail = дії людей/API, Config = стан налаштувань і compliance.

Підсумок: CloudWatch, CloudTrail & Config одним поглядом

  • CloudWatch: метрики + логи + алярми — 'здоров'я і продуктивність' системи в реальному часі
  • CloudTrail: аудит КОЖНОГО API-виклику — хто, що, коли зробив в акаунті
  • Config: стан конфігурації ресурсів У ЧАСІ + перевірка на відповідність правилам (compliance)
  • Разом вони покривають повний цикл 'observability': продуктивність + аудит дій + compliance конфігурації

Коротка формула для іспиту: CloudWatch = 'як почувається', CloudTrail = 'хто зробив', Config = 'як налаштовано'.
