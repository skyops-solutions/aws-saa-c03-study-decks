Проблема, яку вирішує вся ця тема

Проблема tight coupling

Аналогія: пряма телефонна лінія vs поштова скринька

  • Уяви, що Сервіс A дзвонить напряму Сервісу B і ЧЕКАЄ, доки той відповість. Якщо B впаде або буде повільним — A теж 'зависне' або впаде.
  • Це tight coupling (жорсткий зв'язок) — збій в одному місці каскадно ламає все інше.
  • Рішення: замість прямого дзвінка — 'поштова скринька' (черга/топік) між сервісами. A кладе повідомлення і одразу продовжує роботу, не чекаючи B.
  • Це і є decoupling: сервіси працюють НЕЗАЛЕЖНО одне від одного, з різною швидкістю, і можуть падати/масштабуватись окремо.
EXAM TIPЦе один з ключових принципів Well-Architected 'Reliability' стовпа — асинхронна, слабко зв'язана архітектура стійкіша до збоїв.

1. Навіщо Decoupling

Розділ 2

Amazon SQS

Simple Queue Service — черга повідомлень

Що таке SQS? (аналогія)

Поштова скринька 'один до одного'

  • SQS — це черга: Producer кладе повідомлення, ОДИН Consumer забирає і обробляє його (потім видаляє з черги).
  • Pull-based модель: Consumer сам ОПИТУЄ (poll) чергу, питаючи 'чи є нові повідомлення?' — на відміну від SNS, де повідомлення 'штовхають' (push) підписникам.
  • Необмежена пропускна здатність (throughput) для Standard Queue — AWS сам масштабує чергу.
  • Повідомлення зберігається в черзі від 1 хв до 14 днів (за замовчуванням 4 дні), максимальний розмір повідомлення 256 KB.
ЗАПАМ'ЯТАЙSQS = 'один Producer → одна черга → зазвичай кілька Consumer, які РОЗПОДІЛЯЮТЬ роботу між собою' (кожне повідомлення обробляється ОДИН раз).
2. Amazon SQS

Ключові механізми SQS

Найчастіші деталі в питаннях

  • Visibility Timeoutколи Consumer забирає повідомлення, воно 'ховається' від інших на N секунд (типово 30); якщо Consumer не встиг видалити його за цей час — повідомлення знову стає видимим (можлива повторна обробка).
  • Long PollingConsumer чекає ДО 20 секунд на нове повідомлення замість миттєвого порожнього результату — зменшує кількість 'пустих' запитів і costs.
  • Dead Letter Queue (DLQ)повідомлення, що не вдалось обробити N разів (maxReceiveCount), автоматично переміщується в окрему чергу для аналізу помилок.
  • FIFO Queueгарантує строгий порядок і 'рівно один раз' (exactly-once) обробку — але з обмеженим throughput (300-3000 msg/сек) на відміну від Standard.
EXAM TIPStandard Queue: необмежений throughput, 'at-least-once' доставка, порядок НЕ гарантується (можливі дублікати). FIFO: гарантований порядок + exactly-once, але обмежений throughput.
2. Amazon SQS

SQS + Auto Scaling Group

Класичний архітектурний патерн

  • ASG може масштабуватись на основі метрики 'кількість повідомлень у черзі на інстанс' (ApproximateNumberOfMessages / кількість інстансів).
  • Черга росте → ASG додає інстанси для обробки → черга зменшується → ASG зменшує кількість інстансів.
  • Це типовий патерн для batch processing: веб-сервери кладуть завдання в SQS, 'worker' інстанси в ASG обробляють їх незалежно від пікового навантаження на веб-рівні.

Розділ 3

Amazon SNS

Simple Notification Service — pub/sub розсилка

Що таке SNS? (аналогія)

Радіостанція — один голос, багато слухачів

  • SNS — це pub/sub (publish/subscribe): Publisher надсилає ОДНЕ повідомлення в Topic, а ВСІ підписники (subscribers) отримують копію одразу (push, не pull).
  • Підписники можуть бути різних типів: SQS, Lambda, HTTP(S) endpoint, Email, SMS, мобільні push-нотифікації.
  • На відміну від SQS (один Consumer забирає одне повідомлення), у SNS КОЖЕН підписник отримує СВОЮ копію того самого повідомлення.
  • SNS FIFO Topicзвичайний SNS Topic (Standard) НЕ гарантує порядок доставки різним підписникам. Якщо порядок критичний (напр. фінансові транзакції) — існує SNS FIFO Topic, що гарантує строгий порядок і exactly-once доставку, так само як SQS FIFO Queue, але може надсилати тільки в SQS FIFO черги (не в Lambda/HTTP/Email напряму).
EXAM TIPSQS = 'point-to-point' (одне повідомлення обробляється один раз одним з Consumer). SNS = 'broadcast' (усі підписники отримують копію). Пастка: 'SNS завжди best-effort, без гарантії порядку' — правда лише для Standard Topic; якщо потрібен порядок, є SNS FIFO.
3. Amazon SNS

SNS + SQS Fan-Out Pattern

Дуже частий сценарій на іспиті

  • Проблема: якщо Publisher надсилає повідомлення напряму в кілька SQS черг, він мусить сам знати про всі черги і дублювати запис.
  • Рішення (Fan-Out): Publisher надсилає ОДНЕ повідомлення в SNS Topic → SNS автоматично 'розмножує' його у ВСІ підписані SQS черги.
  • Переваги: кожна черга-підписник обробляє повідомлення НЕЗАЛЕЖНО, з власною швидкістю, і навіть якщо один consumer впаде — інші не постраждають (message durability завдяки SQS).
ЗАПАМ'ЯТАЙ'Потрібно, щоб ОДНА подія одночасно тригерила кілька незалежних систем обробки (напр. і аналітику, і email, і оновлення БД)' → SNS + SQS Fan-Out.

Kinesis, Data Firehose, Amazon MQ

Потокова обробка даних у реальному часі

Amazon Kinesis Data Streams

Для дуже великих обсягів даних у реальному часі

  • Уяви конвеєрну стрічку: дані (логи, кліки, IoT-сенсори) течуть безперервно, і КІЛЬКА різних систем можуть 'читати' той самий потік НЕЗАЛЕЖНО одна від одної (на відміну від SQS, де повідомлення зникає після обробки).
  • Дані організовані в Shards — кожен Shard забезпечує 1 MB/сек запису і 2 MB/сек читання; більше Shards = більший throughput.
  • Дані зберігаються в потоці від 1 до 365 днів (за замовчуванням 24 год) — можна 'перечитати' історію, на відміну від SQS.
  • Типове застосування: real-time аналітика, агрегація логів, метрики, клікстрім-аналіз.
EXAM TIPКлючова відмінність від SQS: у Kinesis ОДНІ Й ТІ САМІ дані можуть читати БАГАТО різних споживачів незалежно (дані не видаляються після читання).
4. Kinesis, Data Firehose & Amazon MQ

Третя нога Kinesis: Managed Service for Apache Flink

Не тільки Streams і Firehose

  • Проблема: Data Streams дає тобі 'сирі' дані потоку, але ти сам маєш писати код (Lambda/KCL), щоб виконувати аналітику НАД цим потоком у реальному часі (напр. 'порахувати середнє за останню хвилину', 'знайти аномалії').
  • Amazon Managed Service for Apache Flink (раніше Kinesis Data Analytics) дозволяє писати ЗВИЧАЙНИЙ SQL-запит (або Flink-код) НАПРЯМУ над потоком даних — без розгортання власного кластера обробки чи написання Lambda-коду для кожної метрики.
  • Типове застосування: 'на льоту' агрегувати/фільтрувати потік перед тим, як покласти результат у Data Streams/Firehose/S3 для подальшого зберігання.
ЗАПАМ'ЯТАЙ'Потрібно вважати SQL-подібний запит НАПРЯМУ над потоком даних у реальному часі, без написання Lambda-коду' → Managed Service for Apache Flink, а не Data Streams + custom consumer.

Коли обрати що

Швидкі підказки за ключовими словами

  • "Простий воркер обробляє задачі одну за одною"SQS.
  • "Одна подія має тригерити кілька незалежних систем"SNS (можливо + SQS fan-out).
  • "Потрібна складна кастомна real-time обробка з можливістю 'перечитати' дані"Kinesis Data Streams.
  • "Просто перелити потік логів у S3/Redshift без коду"Kinesis Data Firehose.
  • "Мігруємо legacy застосунок з RabbitMQ/ActiveMQ, міняти протокол не хочемо"Amazon MQ.
EXAM TIPData Firehose НЕ real-time (near real-time, буферизує ~60 сек за замовчуванням) — якщо потрібна справжня мілісекундна обробка, обирай Data Streams. Пастка: Firehose НЕ вміє писати напряму в DynamoDB чи довільну базу даних — лише у свій фіксований список призначень.

Підсумок: Messaging одним поглядом

  • Decoupling — головна ідея: сервіси не мають напряму чекати одне на одного
  • SQS: point-to-point черга, Visibility Timeout, DLQ, Standard (необмежений) vs FIFO (порядок+exactly-once)
  • SNS: pub/sub broadcast, Fan-Out Pattern (SNS → кілька SQS) — типовий exam-сценарій
  • Kinesis Data Streams (custom real-time, багато читачів) vs Data Firehose (авто-доставка, near real-time, без коду)
  • Amazon MQ — для міграції legacy застосунків з існуючими JMS/AMQP протоколами

Ключ до цього розділу — розрізняти 'один consumer забирає' (SQS) від 'усі підписники отримують копію' (SNS) від 'багато читачів того самого потоку' (Kinesis).
