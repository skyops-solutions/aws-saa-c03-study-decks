Розділ 1

AWS KMS

Керування ключами шифрування

Що таке KMS? (аналогія)

Сейф із ключами, який ти ніколи не бачиш напряму

  • Уяви банківський сейф: ти можеш попросити банк 'зашифруй/розшифруй цей документ моїм ключем', але сам фізичний ключ ти НІКОЛИ не тримаєш у руках.
  • KMS керує криптографічними ключами (CMK — Customer Master Key / KMS Key) і виконує шифрування/розшифрування через API — сирий ключовий матеріал не покидає межі KMS.
  • Інтегрований практично з усіма AWS-сервісами: S3, EBS, RDS, Lambda env vars тощо — 'encryption at rest' зазвичай означає 'через KMS'.
  • Envelope Encryption: KMS шифрує не самі дані (це робив би повільно), а Data Key, яким вже шифруються дані локально.
EXAM TIPKMS Key ніколи не покидає сервіс KMS у відкритому вигляді — це і є головна причина, чому він 'безпечний за дизайном'.
1. KMS — Key Management Service

Типи ключів KMS

Хто керує і хто платить

  • AWS Managed KeyAWS сам створює і ротує (раз на рік) — безкоштовно, але без гнучкості (не можна редагувати policy).
  • Customer Managed Key (CMK)ти створюєш, керуєш policy, можеш вмикати/вимикати, ротувати вручну чи автоматично — платиш $1/міс за ключ.
  • AWS Owned Keyприклад: коли S3 шифрує дані за замовчуванням ще ДО того, як ти взагалі щось налаштував — це саме AWS Owned Key. Він не належить твоєму акаунту, ти НІКОЛИ його не побачиш і не зможеш вимкнути/ротувати/перевірити через CloudTrail — і саме тому він НЕ підходить, якщо потрібен аудит використання ключа чи контроль над ним (тоді потрібен Customer Managed Key).
  • Multi-Region Keysтой самий Key ID працює в кількох регіонах — корисно для реплікації зашифрованих даних (S3 CRR) без повторного шифрування.
EXAM TIP'Потрібен повний контроль над key policy й можливість вимкнути ключ' → завжди Customer Managed Key, не AWS Managed.
1. KMS — Key Management Service

KMS API ліміти та Symmetric vs Asymmetric

Деталі, що трапляються на іспиті

  • Symmetric CMK (за замовчуванням)один ключ для шифрування І розшифрування — використовується у 99% сценаріїв AWS-інтеграції.
  • Asymmetric CMKпара public/private ключів — коли розшифрування/підпис має відбуватись ПОЗА AWS (напр. клієнт на своєму пристрої).
  • KMS request quotaвиклики Encrypt/Decrypt/GenerateDataKey мають ліміт запитів/сек (throttling) — для дуже високого навантаження варто кешувати Data Key, а не викликати KMS на кожен файл.
  • Імпортований ключовий матеріал (Imported Key Material)якщо ти сам приносиш свій ключовий матеріал у KMS (замість того, щоб AWS його згенерував) — АВТОМАТИЧНА ротація стає НЕДОСТУПНОЮ. Причина проста: авто-ротація означає 'AWS сам згенерує НОВИЙ ключовий матеріал замість старого' — а якщо матеріал прийшов ЗЗОВНІ (ти сам його створив), AWS фізично не може 'сам вигадати' твій наступний ключ; ти маєш вручну згенерувати й заново імпортувати новий матеріал. Це означає: 'потрібен імпортований ключ І автоматична ротація' — суперечність, яку неможливо задовольнити одночасно.
EXAM TIP'ThrottlingException від KMS при масовому шифруванні' — типова пастка; рішення: Envelope Encryption з кешуванням Data Key, а не виклик KMS на кожен об'єкт. Друга пастка: імпортований ключовий матеріал ЗАВЖДИ виключає авто-ротацію.

2. Secrets Manager & SSM Parameter Store

Коли що обрати

Практичні патерни

  • Якщо потрібна АВТОМАТИЧНА ротація пароля бази даних за розкладом — Secrets Manager (без додаткового коду).
  • Якщо потрібно зберегти конфігурацію застосунку (не обов'язково секретну) дешево і просто — SSM Parameter Store.
  • Обидва сервіси інтегруються з IAM policy для контролю доступу і можуть шифрувати значення через KMS.
ЗАПАМ'ЯТАЙ'Потрібна ротація пароля RDS кожні 30 днів без написання власного коду' → Secrets Manager.

Розділ 3

WAF, Shield, Firewall Manager

Захист від атак на рівні застосунку та мережі

Аналогія: охорона на вході vs охорона периметра

Різні рівні захисту

  • WAF (Web Application Firewall) — 'охоронець на вході', що читає КОЖЕН HTTP-запит і блокує підозрілі (SQL injection, XSS) за правилами (Layer 7).
  • Shield — 'охорона периметра' проти масових DDoS-атак (Layer 3/4) — забезпечує стійкість інфраструктури до обсягу трафіку.
  • WAF підключається ЛИШЕ до сервісів, що самі 'розуміють' HTTP(S)-запити: CloudFront, ALB, API Gateway, AppSync, Cognito User Pools, App Runner, Amplify. Shield Standard — безкоштовний і автоматичний для ВСІХ клієнтів AWS.
EXAM TIPПастка: WAF НЕ можна прикріпити напряму до NLB, до Global Accelerator, до Security Group, чи до S3 bucket policy — якщо в відповіді така пропозиція, вона завжди неправильна. Усі ці сервіси працюють НИЖЧЕ Layer 7 (або взагалі не HTTP), тому не мають 'тіла HTTP-запиту', яке WAF міг би прочитати й перевірити на SQL injection/XSS.

3. WAF, Shield & Firewall Manager

AWS Firewall Manager

Централізоване керування правилами для багатьох акаунтів

  • Дозволяє застосувати ОДНАКОВІ WAF-правила, Shield Advanced, Security Groups одразу на всі акаунти AWS Organization.
  • Вирішує проблему 'кожна команда налаштовує свій WAF по-різному' — централізований compliance для великих організацій.
ЗАПАМ'ЯТАЙ'Потрібно застосувати однакові security-правила на 50 акаунтів AWS Organization одночасно' → Firewall Manager, не ручне налаштування кожного акаунту.

Підсумок: Security & Encryption одним поглядом

  • KMS: керує ключами шифрування, Envelope Encryption, Symmetric (99% випадків) vs Asymmetric
  • Secrets Manager (авто-ротація, дорожче) vs SSM Parameter Store (дешево, ручна ротація)
  • WAF (Layer 7, логіка запиту) + Shield (Layer 3/4, обсяг DDoS) = комплексний захист
  • Firewall Manager — централізоване керування правилами для AWS Organization
  • GuardDuty (аномалії поведінки) / Inspector (вразливості) / Macie (чутливі дані в S3)

Security — домен №1 на іспиті (30%). Ця тема разом з IAM формує основу більшості 'яке рішення найбезпечніше' питань.
