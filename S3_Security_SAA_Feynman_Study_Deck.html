4 методи шифрування S3

SSE-S3, SSE-KMS, SSE-C, Client-Side — хто керує ключем?

SSE-S3 та SSE-KMS

Server-Side Encryption — два "керовані AWS" варіанти

  • SSE-S3ключами повністю керує AWS. Шифрування AES-256. Увімкнено ЗА ЗАМОВЧУВАННЯМ для нових бакетів/об'єктів. Header: x-amz-server-side-encryption: AES256.
  • SSE-KMSключами керує AWS KMS. Переваги: контроль юзера над ключем + аудит використання через CloudTrail. Header: x-amz-server-side-encryption: aws:kms.
  • SSE-KMS Limitationкожен upload/download викликає KMS API (GenerateDataKey/Decrypt) — рахується в KMS quota (5500-30000 req/s залежно від регіону). При масовому трафіку можна впертись у ліміт КVMS, а не S3.
EXAM TIP"Потрібен аудит хто і коли використовував ключ шифрування" → SSE-KMS (через CloudTrail). "Просте шифрування без зайвої складності" → SSE-S3 (дефолт).

1. Шифрування S3

Encryption in Transit + примусове шифрування

SSL/TLS та aws:SecureTransport

  • S3 має 2 endpoints: HTTP (не зашифровано) і HTTPS (зашифровано в дорозі).
  • HTTPS обов'язковий для SSE-C (бо ключ передається в заголовку).
  • Force Encryption in TransitBucket Policy з умовою aws:SecureTransport = false → Deny — примусово блокує будь-який HTTP-доступ до бакету.
EXAM TIP"Default Encryption" на бакеті (SSE-S3/KMS) шифрує дані НА ДИСКУ. Bucket Policy з aws:SecureTransport забезпечує шифрування В ДОРОЗІ. Це два РІЗНІ шари захисту — часто обидва потрібні одночасно.

Контроль доступу та аудит

MFA Delete, Access Logs, Pre-Signed URLs

MFA Delete

Другий фактор для НЕБЕЗПЕЧНИХ операцій

  • Вимагає код з MFA-пристрою ДЛЯ: permanently delete object version, suspend Versioning.
  • НЕ вимагає MFA для: enable Versioning, list deleted versions (тільки перегляд, не видалення).
  • Передумова: Versioning МАЄ бути увімкнений на бакеті.
  • Тільки root account (bucket owner) може вмикати/вимикати MFA Delete — навіть адміни з повними IAM-правами не можуть.
EXAM TIPMFA Delete захищає саме від "випадкового або зловмисного permanent delete" — не плутай з простим блокуванням запису чи звичайним IAM Deny.
2. Контроль доступу

S3 Access Logs — і головна пастка

Логування ВСІХ запитів до бакету

  • Кожен запит до S3 (авторизований чи ні, з будь-якого акаунта) логується в ІНШИЙ S3 bucket.
  • Logging bucket МАЄ бути в тому самому регіоні, що й моніторований бакет.
ПАСТКА ІСПИТУНІКОЛИ не роби logging bucket = сам моніторований bucket! Це створює нескінченний "logging loop" — кожен PutObject логу генерує новий лог-запис, бакет росте експоненційно.
2. Контроль доступу

Pre-Signed URLs

Тимчасовий доступ до приватного об'єкта

  • Генеруються через S3 Console, CLI, чи SDK.
  • Термін дії: Console — 1-720 хвилин (до 12 годин). CLI — параметр --expires-in секундах, дефолт 3600с, максимум 604800с (~168 годин).
  • Юзер з посиланням отримує ПРАВА ТОГО, ХТО ЗГЕНЕРУВАВ URL (для GET/PUT) — тимчасово й обмежено конкретним об'єктом.
  • Use cases: платне відео тільки для залогінених юзерів; динамічний список дозволених завантажень; тимчасовий upload у конкретне місце бакету.
EXAM TIPPre-Signed URL "успадковує" права генератора — якщо в генератора відібрати IAM-права ПІСЛЯ генерації URL, посилання теж перестане працювати (permission real-time, не "заморожена" на момент генерації).

3. Compliance

S3 Access Points

Спрощене керування доступом на масштабі

  • Замість однієї величезної Bucket Policy на весь бакет — окремі Access Points, кожен зі своєю політикою й DNS-іменем.
  • Приклад: Finance-команда отримує Access Point тільки на /finance/* префікс, Sales — тільки на /sales/*, Analytics — read-only на весь бакет.
  • VPC OriginAccess Point можна обмежити доступом ТІЛЬКИ з конкретного VPC — вимагає VPC Endpoint (Gateway чи Interface) з політикою, що дозволяє доступ до бакету й Access Point.
ЗАПАМ'ЯТАЙAccess Points вирішують проблему "одна гігантська Bucket Policy стає некерованою при рості кількості команд/відділів" — розбиваєш на менші, незалежно керовані шматки.

3. Compliance

Підсумок: S3 Security одним поглядом

  • 4 шифрування: SSE-S3 (дефолт, AWS керує) → SSE-KMS (аудит через CloudTrail, KMS quota ліміти) → SSE-C (твій ключ, HTTPS обов'язково) → Client-Side (S3 взагалі не бачить plaintext)
  • Encryption at rest (Default Encryption) ≠ Encryption in transit (aws:SecureTransport Bucket Policy) — різні шари
  • MFA Delete захищає permanent delete + suspend versioning, керується ТІЛЬКИ root-акаунтом
  • НІКОЛИ logging bucket = моніторований bucket (logging loop)
  • Pre-Signed URL = тимчасові права генератора. Object Lock Compliance mode = навіть root не видалить
  • Access Points = дроблення однієї Bucket Policy на керовані шматки, з опцією VPC-only доступу

S3 Security — глибока тема з багатьма деталями-пастками. Особливо звертай увагу на різницю Compliance vs Governance mode.
