Розділ 1

AWS Lambda

Код без серверів, які треба керувати

Що таке Lambda? (як для 5-річного)

Проста аналогія

  • Уяви, що замість оренди цілого офісу (EC2-сервер, що працює 24/7) ти платиш комусь лише за ХВИЛИНИ, коли він реально виконує твоє доручення.
  • Lambda — це функція (код), яку AWS запускає у відповідь на подію (HTTP-запит, файл в S3, повідомлення в SQS тощо), а потім вимикає.
  • Платиш тільки за: кількість викликів + час виконання (мс) + виділену пам'ять. Немає викликів — немає оплати.
  • AWS сам масштабує кількість паралельних виконань — від 0 до тисяч інстансів функції за секунди.
EXAM TIPLambda — це FaaS (Function as a Service), найчистіша форма serverless: ти НІКОЛИ не бачиш і не патчиш операційну систему.
1. AWS Lambda

Ліміти Lambda

Мастхев напам'ять для іспиту

  • Час виконаннямаксимум 15 хвилин на один виклик (timeout).
  • Пам'ять128 MB – 10,240 MB (10 GB); CPU масштабується пропорційно виділеній пам'яті.
  • Розмір deployment package50 MB (zip, через консоль) / 250 MB (unzipped, з layers) / до 10 GB через Container Image.
  • /tmp дисковий простірдо 10 GB тимчасового сховища (очищається між 'холодними' стартами).
  • Env variablesдо 4 KB.
EXAM TIP'Задача виконується довше 15 хвилин' → Lambda НЕ підходить, потрібен ECS/Fargate, Batch, або Step Functions для розбиття на кроки.
1. AWS Lambda

Concurrency (одночасність)

Ключова тема для 'сплесків' навантаження

  • Concurrency Limitскільки Lambda-виконань може працювати ОДНОЧАСНО в акаунті/регіоні (за замовчуванням 1000, можна підняти запитом до AWS).
  • Reserved Concurrencyгарантує (і одночасно ОБМЕЖУЄ) конкретній функції певну кількість одночасних виконань — захищає інші функції від 'зʼїдання' всього ліміту однією 'жадібною' функцією.
  • Provisioned Concurrencyтримає N 'прогрітих' (warm) інстансів функції заздалегідь — прибирає cold start latency для критичних до затримки застосунків.
  • Throttlingякщо ліміт вичерпано — нові виклики отримують помилку 429 (TooManyRequestsException) або ставляться в чергу залежно від тригера.
ЗАПАМ'ЯТАЙ'Потрібна передбачувана низька latency без cold start для критичного API' → Provisioned Concurrency.
1. AWS Lambda

Lambda у VPC та тригери

Архітектурні деталі

  • Lambda за замовчуваннямне в твоїй VPC — має прямий доступ до інтернету й публічних AWS API (S3, DynamoDB), але НЕ бачить приватні ресурси (RDS у приватній підмережі).
  • Lambda в VPCотримує ENI в твоїй підмережі — тепер бачить приватні ресурси, але сам потребує NAT Gateway для виходу в інтернет.
  • Типові тригериAPI Gateway (HTTP), S3 (file upload), DynamoDB Streams, SQS, SNS, EventBridge (за розкладом чи подіями), CloudFront (Lambda@Edge).
  • Lambda@Edge — чим відрізняється від звичайної Lambdaзвичайна Lambda виконується в ОДНОМУ регіоні — кожен запит користувача з іншого кінця світу мусить 'долетіти' до цього регіону. Lambda@Edge розгортає ТУ САМУ функцію на CloudFront Edge Locations по всьому світу — код виконується БЛИЗЬКО до користувача, перехоплюючи запит/відповідь (viewer request/response, origin request/response) ще до того, як трафік взагалі дійде до origin-сервера. Це прибирає 'подорож' до основного регіону для простої логіки (напр. редірект за країною, модифікація заголовків).
  • SnapStartпроблема: Java-функції мають особливо повільний cold start, бо перед кожним 'холодним' викликом JVM повинна заново стартувати, завантажити всі класи і ініціалізувати фреймворк — це може займати секунди. SnapStart один раз (при публікації версії) повністю ІНІЦІАЛІЗУЄ функцію, робить 'знімок' (snapshot) готового до роботи стану пам'яті й диска, і зберігає його. Наступні холодні старти не виконують ініціалізацію заново — вони просто 'розморожують' готовий знімок, що на порядки швидше.
EXAM TIPСценарій 'Lambda має звертатись до RDS у приватній підмережі' → Lambda має бути розгорнута В цій VPC (і в тій самій підмережі/SG, що й RDS).

Розділ 2

Amazon DynamoDB

NoSQL база даних — швидкість за будь-якого масштабу

Що таке DynamoDB? (аналогія)

Величезна картотека з ключами замість SQL-таблиць

  • На відміну від RDS (реляційна, SQL, ACID-транзакції зі складними JOIN), DynamoDB — це NoSQL key-value/document база.
  • Немає фіксованої схеми (кожен 'запис'-item може мати різні атрибути) — гнучкість замість строгої структури.
  • Автоматично масштабується горизонтально на necessity — немає 'вертикального ліміту' одного сервера, як у RDS.
  • Однозначна latency в одиниці мілісекунд незалежно від розміру таблиці (терабайти даних — без проблем).
EXAM TIPDynamoDB НЕ підходить, якщо потрібні складні JOIN-запити між таблицями або складна аналітика — для цього RDS/Redshift/Athena.
2. Amazon DynamoDB

Primary Key: Partition Key vs Sort Key

Найважливіша концепція для дизайну таблиці

  • Partition Key (Hash Key)визначає, НА ЯКОМУ фізичному 'розділі' (partition) зберігається item; DynamoDB хешує його для рівномірного розподілу навантаження.
  • Sort Key (Range Key, опційно)разом з Partition Key утворює складений первинний ключ — дозволяє зберігати КІЛЬКА items з однаковим Partition Key, відсортованих за Sort Key.
  • Погано обраний Partition Key= 'hot partition' — весь трафік іде в один розділ, продуктивність падає (класична помилка дизайну, часто в питаннях).
EXAM TIPОбирай Partition Key з ВИСОКОЮ кардинальністю (багато унікальних значень), щоб рівномірно розподілити навантаження між розділами.

Як платити за пропускну здатність

РежимОписКоли обрати
Provisionedзаздалегідь задаєш RCU/WCU (Read/Write Capacity Units); можна додати Auto Scaling для коригуванняПередбачуване, стабільне навантаження — дешевше за довгий термін
On-Demandплатиш за фактичні read/write запити, без планування capacityНепередбачуване або спайкове навантаження, нові застосунки
2. Amazon DynamoDB

Просунуті фічі DynamoDB

Часто зустрічаються у сценаріях

  • DynamoDB Accelerator (DAX)in-memory кеш ПЕРЕД DynamoDB (мікросекундна latency); прозорий для застосунку — сумісний з DynamoDB API.
  • DynamoDB Streamsпотік змін таблиці (create/update/delete) — тригерить Lambda для реакції в реальному часі (напр. аудит, реплікація).
  • Global Tablesмульти-регіональна, active-active реплікація — читання/запис у будь-якому регіоні з автоматичним merge conflict resolution.
  • TTL (Time To Live)автоматичне видалення застарілих items (напр. сесії, тимчасові дані) без додаткової оплати за запис на видалення.
  • TransactionsACID-транзакції для кількох items/таблиць одночасно (all-or-nothing).
  • PITR (Point-In-Time Recovery) vs On-Demand BackupPITR відновлює таблицю на БУДЬ-ЯКУ секунду за останні 35 днів — ідеально для 'хтось випадково зіпсував дані вчора о 14:32, відкотити саме на цей момент'. On-Demand Backup — це backup на КОНКРЕТНИЙ момент, який ти сам ініціюєш ЗАЗДАЛЕГІДЬ; не можна 'заднім числом' створити backup на вчорашню дату, якщо PITR не був увімкнений.
ЗАПАМ'ЯТАЙ'Потрібна мікросекундна latency для читання' → DAX. 'Реакція в реальному часі на зміни' → DynamoDB Streams + Lambda. 'Відновити на довільний момент часу в минулому' → лише PITR, backup заднім числом не створити.

API Gateway, Step Functions, Cognito

З'єднуємо все в застосунок

API Gateway

Вхідні двері для serverless-застосунку

  • Що робитьприймає HTTP(S)-запити ззовні і маршрутизує їх до Lambda, іншого AWS-сервісу, або навіть до звичайного HTTP-бекенду.
  • Типи APIREST API (повнофункціональний, більше можливостей), HTTP API (простіший, дешевший, швидший), WebSocket API (для двостороннього realtime-зв'язку).
  • API Key vs Usage PlanAPI Key — це просто ІДЕНТИФІКАТОР конкретного клієнта (хто звертається). Usage Plan — це ОБ'ЄКТ, що реально тримає ліміти (запитів/сек, квота на місяць) і прикріплюється до одного чи кількох API Keys. Тобто: Key каже 'хто ти', Plan каже 'скільки тобі можна' — вони завжди працюють РАЗОМ, окремо один без одного throttling не зробити.
  • Lambda Authorizerколи готові механізми (IAM, Cognito) не підходять під твою логіку автентифікації (напр. власний JWT-формат чи стороння система логіну) — Lambda Authorizer це ЗВИЧАЙНА Lambda-функція, яку API Gateway викликає ПЕРЕД основною Lambda; вона перевіряє токен/заголовок і повертає IAM-policy (Allow/Deny) — API Gateway далі керується цим рішенням.
  • Кешування відповідей та трансформація запитів/відповідейдодаткові вбудовані фічі API Gateway для зниження навантаження на backend і адаптації формату даних без зміни коду Lambda.
  • Stages & Canary Deploymentsверсіонування API (dev/prod) і поступовий (canary) розкат нової версії з відсотком трафіку.
ЗАПАМ'ЯТАЙThrottling в API Gateway захищає Lambda від DDoS/перевантаження ще ДО того, як запит взагалі дійде до функції. Пастка: ALB/NLB/GWLB НЕ мають вбудованого per-client rate limiting з API Keys/Usage Plans — це унікальна фіча САМЕ API Gateway серед усіх 'вхідних точок' AWS.
3. API Gateway, Step Functions & Cognito

AWS Step Functions

Оркестрація складних workflow

  • Уяви блок-схему (state machine): крок 1 → крок 2 → якщо помилка, повтори крок 2 → крок 3 — і все це БЕЗ написання коду для самої оркестрації.
  • Кожен 'крок' (state) зазвичай викликає Lambda, але може викликати й інші AWS-сервіси напряму (ECS Task, SNS, SQS, тощо).
  • Вбудована підтримка retry-логіки, error handling, паралельного виконання гілок, і human-approval кроків (чекати на зовнішню подію).
  • Ідеально для довгих (>15 хв) або складних багатокрокових бізнес-процесів — обходить ліміт часу виконання Lambda.
ЗАПАМ'ЯТАЙ'Потрібен складний, багатокроковий процес з retry/error handling і візуалізацією стану' → Step Functions замість оркестрації всередині однієї Lambda.

Amazon Cognito

Автентифікація користувачів для мобільних/веб-застосунків

КомпонентЩо робить
User Poolsкерована 'база користувачів' — sign-up/sign-in, MFA, відновлення пароля, видає JWT токени після успішного логіну
Identity Pools (Federated Identities)видає ТИМЧАСОВІ AWS-креденшели (через STS) користувачам — щоб вони могли напряму звертатись до AWS-сервісів (напр. S3) з мобільного застосунку
ІнтеграціяUser Pool автентифікує 'хто ти', Identity Pool дає 'що тобі можна робити в AWS' — часто працюють РАЗОМ
EXAM TIPПлутанина в питаннях: User Pool = автентифікація (логін), Identity Pool = авторизація для доступу до AWS-ресурсів (тимчасові credentials).

Підсумок: Serverless одним поглядом

  • Lambda: платиш за виконання, макс. 15 хв, пам'ять 128MB-10GB, Reserved vs Provisioned Concurrency
  • DynamoDB: NoSQL, Partition Key визначає розподіл навантаження, DAX для мікросекундної latency, Streams для реакції в реальному часі
  • API Gateway: вхідна точка + throttling + auth; Step Functions: оркестрація складних workflow без ліміту 15 хв
  • Cognito: User Pools (автентифікація) + Identity Pools (тимчасові AWS credentials) — часто працюють разом

Serverless-архітектури — це 'Performance Efficiency' стовп Well-Architected. Пам'ятай: немає серверів для патчингу = менше operational overhead.
