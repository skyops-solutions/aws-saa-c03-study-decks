Розділ 1

VPC, Subnets, CIDR

Твоя приватна мережа всередині AWS

Що таке VPC? (як для 5-річного)

Аналогія: приватна територія в місті

  • Уяви, що AWS — величезне місто, а VPC — це твоя приватна огороджена територія в ньому, де ти сам вирішуєш, як розділити простір (підмережі), хто входить і виходить (маршрути, firewall).
  • VPC = ізольована віртуальна мережа в межах одного AWS-регіону (не виходить за межі регіону).
  • CIDR блок (напр. 10.0.0.0/16) визначає діапазон IP-адрес твоєї VPC — 65,536 адрес у /16.
  • Кожна Subnet (підмережа) прив'язана РІВНО до ОДНІЄЇ Availability Zone і має СВІЙ менший CIDR-діапазон (напр. 10.0.1.0/24).
EXAM TIPУ кожній subnet AWS резервує 5 IP-адрес (перші 4 і остання) — вони недоступні для твоїх інстансів (напр. .0 мережа, .1 router, .2 DNS, .3 резерв, .255 broadcast).
1. VPC & Subnets

Public vs Private Subnet

Що визначає 'публічність'

  • Subnet вважається Public, якщо її Route Table має маршрут 0.0.0.0/0 → Internet Gateway.
  • Subnet вважається Private, якщо такого прямого маршруту до IGW немає (навіть якщо теоретично є публічний IP на інстансі).
  • Публічність — це властивість МАРШРУТИЗАЦІЇ, а не самого інстансу чи субнету 'за замовчуванням'.
EXAM TIPКласична пастка: 'у інстанса є публічний IP, але інтернет не працює' → перевір, чи в Route Table підмережі взагалі є маршрут на Internet Gateway.

Розділ 2

Internet Gateway, NAT, Bastion

Як приватні ресурси виходять в інтернет

Internet Gateway (IGW)

Двері назовні для публічної підмережі

  • IGW — це компонент VPC (один на VPC), що дозволяє двосторонній трафік між VPC і інтернетом.
  • Сам по собі нічого не робить, доки Route Table підмережі не має маршруту 0.0.0.0/0 → IGW.
  • Безкоштовний і горизонтально масштабований AWS-сервіс — не треба ним 'керувати'.
  • Хто саме робить NAT для інстансу з публічною IP?несподівано — САМ Internet Gateway. Коли твій інстанс у публічній підмережі має Public/Elastic IP, це САМЕ IGW підміняє його приватну IP (10.0.x.x) на публічну і назад (1:1 NAT) при проходженні трафіку. NAT Gateway — це ОКРЕМИЙ інструмент, потрібний ЛИШЕ для інстансів у ПРИВАТНІЙ підмережі, які не мають власної публічної IP.
EXAM TIPПастка практичних тестів: 'який компонент виконує translation адрес для інстансу з публічною IP в публічній підмережі' — відповідь IGW, НЕ NAT Gateway (NAT Gateway тут навіть не задіяний).
2. Internet Access & NAT

NAT Gateway vs NAT Instance vs Bastion Host

Головна порівняльна таблиця розділу

  • NAT Gatewayкерований AWS сервіс — дозволяє інстансам у ПРИВАТНІЙ підмережі виходити в інтернет (напр. для оновлень), але забороняє вхідні з'єднання ЗЗОВНІ. Ставиться в ПУБЛІЧНІЙ підмережі.
  • NAT Instanceзастаріліший підхід — звичайний EC2 з увімкненим IP forwarding; треба самому патчити, масштабувати, і вимкнути Source/Dest Check.
  • Bastion Hostзвичайний EC2 у публічній підмережі, через який адміністратори SSH/RDP-яться до інстансів у ПРИВАТНИХ підмережах. Не плутай з NAT — Bastion для ВХІДНОГО адмін-доступу, NAT для ВИХІДНОГО трафіку.
EXAM TIPNAT Gateway — це односторонній вихід (приватна підмережа → інтернет). Bastion Host — це вхідний доступ ЛЮДИНИ до приватної підмережі. Це РІЗНІ задачі, які часто плутають.
2. Internet Access & NAT

NAT Gateway — деталі для іспиту

  • Прив'язаний до КОНКРЕТНОЇ AZ — для відмовостійкості потрібен окремий NAT Gateway в КОЖНІЙ AZ (інакше при падінні AZ втрачаєш вихід в інтернет для всіх приватних підмереж).
  • Автоматично масштабується до 45 Гбіт/с, не потребує патчів — на відміну від NAT Instance.
  • Egress-Only Internet Gatewayчому НЕ можна просто взяти звичайний NAT Gateway для IPv6? Бо NAT (Network Address Translation) взагалі існує через дефіцит IPv4-адрес — приватні IPv4 (10.0.0.0/16) не можна маршрутизувати в інтернет напряму, тому їх треба 'підміняти' на публічну адресу. У IPv6 адрес вистачає на всіх — КОЖНА IPv6-адреса вже глобально унікальна і технічно маршрутизована, тому 'підміняти' нічого не треба. Залишається лише одна задача: дозволити вихідний трафік, але заблокувати НЕЗАПРОШЕНИЙ вхідний — саме це й робить Egress-Only IGW, не займаючись підміною адрес.
ЗАПАМ'ЯТАЙ'High Availability для NAT' у формулюванні задачі → потрібен NAT Gateway у КОЖНІЙ AZ, а не один на всю VPC.

3. Security: NACL vs SG, VPC Peering & Endpoints

VPC Peering

З'єднання двох VPC як єдиної мережі

  • Дозволяє двом VPC (навіть у різних акаунтах/регіонах) обмінюватись трафіком напряму через приватні IP, ніби вони в одній мережі.
  • CIDR-блоки VPC, що з'єднуються, НЕ МОЖУТЬ перетинатись (overlap) — часта пастка в дизайні.
  • Не транзитивний: якщо VPC A ⟷ B і B ⟷ C, то A НЕ бачить C автоматично — треба окремий peering A ⟷ C.
EXAM TIP'Транзитивність' між VPC — це те, чого VPC Peering НЕ вміє. Якщо потрібно з'єднати багато VPC між собою — відповідь Transit Gateway, а не купа Peering-з'єднань.
3. Security: NACL vs SG, VPC Peering & Endpoints

VPC Endpoints

Приватний доступ до AWS-сервісів без інтернету

  • Gateway EndpointТІЛЬКИ для S3 і DynamoDB (більше ні для чого) — це найстаріший тип VPC-ендпоінта, створений ще до появи PrivateLink саме для двох сервісів із найбільшим обсягом трафіку (масові дані в S3, і DynamoDB, що часто викликається з кожного запиту застосунку). Тому він простіший (просто маршрут у Route Table, без ENI) і безкоштовний. Усі сервіси, додані ПІСЛЯ, підключаються вже через новіший, універсальніший механізм — Interface Endpoint.
  • Interface Endpoint (PrivateLink)для ВСІХ ІНШИХ сервісів (SQS, SNS, Kinesis, KMS тощо) — S3/DynamoDB тут виняток, не правило; створює ENI з приватним IP; платний за годину + за трафік.
  • Навіщоінстанс у ПРИВАТНІЙ підмережі (без NAT Gateway/IGW) все одно може звертатись до S3/DynamoDB/інших сервісів, не виходячи в публічний інтернет.
EXAM TIPПастка: 'потрібен Gateway Endpoint для SQS' — неможливо, Gateway Endpoint існує ЛИШЕ для S3 і DynamoDB. Для SQS/SNS/Kinesis/KMS завжди Interface Endpoint (PrivateLink).
3. Security: NACL vs SG, VPC Peering & Endpoints

AWS Resource Access Manager (RAM) — спільне використання VPC

Дешевша альтернатива Transit Gateway для довіреної команди

  • Проблема: кожна команда створює СВОЮ окрему VPC — це означає окремі NAT Gateway (платні), окремі VPC Peering-з'єднання, і складнішу мережу.
  • AWS RAM дозволяє ОДНІЙ команді (власнику VPC) 'поділитися' своїми підмережами з ІНШИМИ акаунтами в тій самій AWS Organization — інші акаунти запускають ресурси ПРЯМО в спільних підмережах, ніби це їхня власна VPC.
  • Дешевше за Transit Gateway (немає погодинної оплати за приєднання) — підходить, коли команди довіряють одна одній і працюють як 'один великий проєкт', а не як ізольовані бізнес-одиниці.
ЗАПАМ'ЯТАЙ'Кілька команд в одній організації хочуть спільну мережу БЕЗ витрат на Transit Gateway чи Peering' → VPC Sharing через AWS RAM — найдешевший варіант, якщо потрібна саме довірена спільна інфраструктура.
3. Security: NACL vs SG, VPC Peering & Endpoints

VPC Lattice

Новіший сервіс — коли мова про сервіси, а не мережі

  • Проблема: у великій мікросервісній архітектурі з'єднати сервіси через VPC Peering/Transit Gateway означає керувати мережею на рівні IP/підмереж — а розробнику насправді потрібно просто 'викликати сервіс Б із сервісу А', незалежно від того, в якій вони VPC чи навіть акаунті.
  • VPC Lattice дає рівень абстракції ВИЩЕ за мережу: реєструєш сервіси (не VPC), налаштовуєш IAM-політики доступу МІЖ сервісами, і Lattice сам вирішує маршрутизацію, балансування навантаження, і навіть роботу між VPC/акаунтами — без Peering, без Transit Gateway, без керування CIDR-блоками.
ЗАПАМ'ЯТАЙ'Потрібно з'єднати мікросервіси з різних VPC/акаунтів на рівні 'сервіс викликає сервіс', не переймаючись мережевою топологією' → VPC Lattice — новіший сервіс, що абстрагує мережу geть.

4. Hybrid Connectivity

Коли що застосовувати

Типові формулювання завдань

  • "Потрібна стабільна низька latency, готові платити більше"Direct Connect.
  • "Потрібно швидко і дешево, можна трохи вищу latency"Site-to-Site VPN.
  • "Десятки VPC мають спілкуватися між собою і з on-premises"Transit Gateway (замість N×N Peering з'єднань).
  • "Потрібна резервна лінія на випадок падіння основного каналу"Direct Connect + VPN backup.
ЗАПАМ'ЯТАЙTransit Gateway підтримує і VPC-to-VPC, і VPC-to-on-premises (через VPN/DX) з одного централізованого місця — думай про нього як про 'мережевий роутер' для всього AWS-акаунту/організації.
4. Hybrid Connectivity

Direct Connect: Public VIF vs Private VIF

Деталь, яку часто пропускають

  • Private Virtual Interface (VIF)дає доступ ЛИШЕ до ресурсів усередині твоєї VPC (приватні IP) — типовий вибір для 'звичайного' гібридного доступу до EC2/RDS у VPC.
  • Public Virtual Interface (VIF)дає доступ до ПУБЛІЧНИХ AWS-сервісів (S3, DynamoDB API тощо) НАПРЯМУ через Direct Connect, минаючи інтернет — потрібен, якщо хочеш звертатись до S3 по приватному каналу DX, а не через VPC Endpoint.
  • Пастка'налаштували Private VIF + VPC Endpoint і чекаємо доступ до S3 через DX' — Private VIF сам по собі НЕ бачить публічні AWS API; для доступу до S3 напряму через DX (без проходження інтернету) потрібен САМЕ Public VIF.
  • Direct Connect Gatewayдозволяє ОДНОМУ Direct Connect з'єднанню давати доступ до КІЛЬКОХ VPC у РІЗНИХ регіонах одночасно — вирішує проблему 'один DX на один регіон'.
EXAM TIPЯкщо сценарій каже 'доступ до S3 через Direct Connect без проходження через публічний інтернет' — перевір, чи згадано САМЕ Public VIF, а не тільки Private VIF.

4. Hybrid Connectivity

Підсумок: VPC одним поглядом

  • VPC/Subnet/CIDR: твоя ізольована мережа, підмережа прив'язана до однієї AZ, публічність визначається Route Table
  • IGW дає доступ в інтернет; NAT Gateway — вихідний доступ для приватних підмереж; Bastion Host — вхідний адмін-доступ
  • SG (stateful, instance-level, allow-only) vs NACL (stateless, subnet-level, allow+deny) — одна з найчастіших пар питань
  • VPC Peering не транзитивний → Transit Gateway для складних топологій; VPC Endpoints — приватний доступ до AWS-сервісів
  • Hybrid: VPN (швидко, через інтернет) vs Direct Connect (стабільно, приватно, довше налаштовувати)

VPC — технічно найскладніша тема іспиту. Намалюй схему VPC на аркуші паперу від руки — це сильно допомагає закріпити розуміння.
