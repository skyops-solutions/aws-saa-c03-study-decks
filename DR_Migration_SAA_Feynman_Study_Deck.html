Розділ 1

RPO, RTO та стратегії Disaster Recovery

Скільки даних і часу ти готовий втратити

RPO vs RTO (аналогія)

Останній збережений файл vs час на перезапуск гри

  • RPO (Recovery Point Objective)'скільки даних я готовий втратити?' — точка в часі, до якої можна відновити дані. Якщо останній backup був годину тому — RPO = 1 година (втратиш зміни за цю годину).
  • RTO (Recovery Time Objective)'скільки часу застосунок може бути НЕДОСТУПНИЙ?' — максимально прийнятний час простою до повного відновлення роботи.
  • Аналогія з відеогроюRPO — це 'з якого save-файлу ти відновишся' (втратив прогрес після останнього збереження). RTO — це 'скільки часу займе завантажити гру заново'.
  • Чим менші RPO/RTOтим ДОРОЖЧЕ рішення — 'нуль втрачених даних, нуль простою' коштує значно більше, ніж 'можемо почекати кілька годин'.
EXAM TIPПерше, що треба зробити в задачі на DR: знайти в умові слова 'скільки даних можна втратити' (RPO) і 'скільки часу можна бути offline' (RTO) — вони визначають, яка стратегія підходить.

Розділ 2

AWS DRS та MGN

Автоматизована реплікація серверів у хмару

AWS Elastic Disaster Recovery (DRS)

Постійна реплікація on-premises серверів у AWS 'про запас'

  • Встановлюєш легкий агент на on-premises (чи інший хмарний) сервер — він БЕЗПЕРЕРВНО реплікує диски сервера у 'легку' (low-cost) стейджинг-область в AWS.
  • У звичайному режимі в AWS НЕ працює повноцінна копія сервера — лише накопичуються дані реплікації (дешево).
  • При катастрофі ('failover') DRS за хвилини піднімає ПОВНОЦІННІ EC2-інстанси з накопичених даних — це і є 'Pilot Light'/'Warm Standby' підхід, АВТОМАТИЗОВАНИЙ сервісом.
EXAM TIPDRS = 'сервіс для DR' (тимчасове перемикання при катастрофі, з наміром повернутись on-premises чи лишитись в AWS за потреби).
2. Elastic Disaster Recovery (DRS) & Application Migration (MGN)

AWS Application Migration Service (MGN)

Схожа технологія, інша МЕТА

  • MGN використовує ТУ САМУ технологію реплікації, що й DRS (агент на сервері, безперервна реплікація дисків), — але мета ОСТАТОЧНА міграція, а не аварійне перемикання.
  • 'Lift-and-shift' підхід: переносиш сервер 'як є' в AWS, без переписування застосунку.
  • Різниця DRS vs MGN — не в технології, а в НАМІРІ: DRS = 'тримати про запас на випадок катастрофи', MGN = 'переїжджаємо назавжди'.
ЗАПАМ'ЯТАЙПитання іспиту 'хочемо ПОСТІЙНО перенести сервери в AWS' → MGN. 'Хочемо мати DR-план на випадок збою основного дата-центру' → DRS. Технологія та сама, мета — різна.

Розділ 3

Database Migration Service, AWS Backup

Спеціалізовані інструменти для баз даних і бекапів

AWS Database Migration Service (DMS)

Перенесення бази даних з мінімальним простоєм

  • Переносить дані з БУДЬ-ЯКОЇ джерельної бази (on-premises MySQL, Oracle, тощо) в AWS (RDS, Aurora, Redshift тощо) — навіть МІЖ різними движками.
  • Continuous Data Replication: джерельна БД лишається ПОВНІСТЮ робочою під час міграції — DMS безперервно копіює зміни, поки не настане момент фінального перемикання (мінімальний downtime).
  • AWS Schema Conversion Tool (SCT) використовується РАЗОМ з DMS, коли рушії відрізняються (напр. Oracle → PostgreSQL) — конвертує схему й код (procedures/views), а DMS переносить самі дані.
EXAM TIP'Потрібно мігрувати production-базу даних БЕЗ значного простою' → DMS з Continuous Replication, а не 'просто зробити дамп і залити'.
3. DMS, AWS Backup та інші інструменти міграції

AWS Backup

Централізоване керування бекапами для БАГАТЬОХ сервісів

  • Замість того, щоб налаштовувати бекапи ОКРЕМО для EBS, RDS, DynamoDB, EFS, кожен по-своєму — AWS Backup дає ОДНУ централізовану policy ('Backup Plan') для всіх одразу.
  • Кросс-регіон і кросс-акаунт backup з коробкинавіщо саме кросс-АКАУНТ: якщо бекап зберігається в ТОМУ Ж акаунті, що й оригінальні дані, і цей акаунт скомпрометовано (напр. ransomware чи зловмисний інсайдер) — зловмисник може видалити ОДНОЧАСНО і дані, і їхній backup. Копіювання backup у ОКРЕМИЙ, ізольований акаунт (до якого немає прямого доступу з 'робочого' акаунту) захищає саме від цього сценарію.
  • Life-cycle правилаавтоматичний перехід старих бекапів у дешевше 'холодне' сховище (Backup Vault Cold Storage), як Lifecycle Rules в S3 — компроміс той самий: дешевше зберігання, але повільніше й дорожче відновлення, тому підходить лише для бекапів, які рідко (чи ніколи) не доводиться реально відновлювати.
ЗАПАМ'ЯТАЙ'Потрібна ОДНА централізована backup-політика для EBS + RDS + DynamoDB одночасно' → AWS Backup, а не налаштування кожного сервісу окремо.

Підсумок: DR & Migrations одним поглядом

  • RPO (скільки даних втратимо) і RTO (скільки часу простою) визначають стратегію: Backup&Restore → Pilot Light → Warm Standby → Multi-Site
  • DRS: автоматизована реплікація 'про запас' для аварійного перемикання (тимчасово або постійно)
  • MGN: та сама технологія, але мета — ОСТАТОЧНА міграція ('lift-and-shift') в AWS
  • DMS (+SCT для різних рушіїв): міграція БД з мінімальним downtime через continuous replication
  • AWS Backup: централізована backup-політика для багатьох AWS-сервісів одночасно

Ключ до цього розділу — швидко визначати RPO/RTO зі сценарію, а потім підбирати ІНСТРУМЕНТ (DRS/MGN/DMS/Backup) під конкретну задачу (сервери vs БД vs загальний backup).
